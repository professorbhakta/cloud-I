0. BASIC TERMINOLOGIES (FOUNDATION)
================================================================================

------------------------------------------------------------------------
0.1 VIRTUALIZATION  ★
------------------------------------------------------------------------
DEFINITION:
  Virtualization is the technology of creating a virtual (logical) version of
  computing resources — such as servers, storage, networks, or operating systems —
  on top of physical hardware, so multiple isolated environments can share the
  same physical machine.

IMPORTANT FACTORS:
  • Separates logical resources from physical hardware
  • Enables multi-tenancy and higher utilization
  • Foundation of modern cloud IaaS

REAL-LIFE EXAMPLES:
  • Running Windows inside VirtualBox on a laptop
  • Creating multiple VMs on one physical server in a data center


------------------------------------------------------------------------
0.2 VIRTUAL MACHINE (VM)
------------------------------------------------------------------------
DEFINITION:
  A software-based computer that behaves like a physical computer, with its own
  virtual CPU, memory, storage, and network interfaces, running a guest OS.

IMPORTANT FACTORS:
  • Isolated from other VMs on the same host
  • Can be started, stopped, cloned, snapshotted, migrated
  • Consumes a share of host CPU/RAM/disk/network

REAL-LIFE EXAMPLES:
  • GCP Compute Engine VM for a Linux practical
  • AWS EC2 instance hosting a website


------------------------------------------------------------------------
0.3 HOST vs GUEST
------------------------------------------------------------------------
HOST:
  The physical machine (and its host OS, if any) that provides resources.

GUEST:
  The virtual machine / OS running on top of the host via virtualization.

REAL-LIFE EXAMPLE:
  Laptop (host) running Ubuntu VM (guest) for testing.


------------------------------------------------------------------------
0.4 HYPERVISOR (VMM — Virtual Machine Monitor)  ★
------------------------------------------------------------------------
DEFINITION:
  Software (or firmware) layer that creates, runs, and manages virtual machines
  by multiplexing physical hardware among guests.

IMPORTANT FACTORS:
  • Controls CPU scheduling, memory allocation, device access
  • Critical for isolation and performance
  • Two main types: Type-1 and Type-2

REAL-LIFE EXAMPLES:
  • VMware ESXi, Microsoft Hyper-V, KVM, Xen (Type-1 style / bare-metal class)
  • Oracle VirtualBox, VMware Workstation (Type-2 / hosted)


------------------------------------------------------------------------
0.5 VIRTUAL HARDWARE
------------------------------------------------------------------------
DEFINITION:
  Emulated or paravirtual devices presented to a guest OS (vCPU, vRAM, vNIC,
  virtual disks).

IMPORTANT FACTORS:
  • Guest thinks it has real devices
  • Hypervisor maps virtual devices to physical resources


------------------------------------------------------------------------
0.6 ISOLATION, CONSOLIDATION, OVERCOMMITMENT
------------------------------------------------------------------------
ISOLATION:
  One VM’s failure/security issue should not freely affect others.

CONSOLIDATION:
  Running many workloads on fewer physical servers.

OVERCOMMITMENT:
  Allocating more virtual resources than physical capacity (carefully), relying
  on not all VMs peaking at once.

IMPORTANT FACTORS:
  • Overcommitment improves density but risks contention if misplanned


------------------------------------------------------------------------
0.7 CONTAINER vs VM (SHORT CONTEXT)
------------------------------------------------------------------------
VM: full guest OS + virtual hardware (heavier, stronger isolation traditionally)
Container: shares host OS kernel; packages app + libs (lighter, faster start)

IMPORTANT FACTORS:
  • Both used in cloud; syllabus focus here is classical virtualization/VMs
  • Containers often run on VMs in public cloud for extra isolation

1. INTRODUCTION TO VIRTUALIZATION  ★★
================================================================================

------------------------------------------------------------------------
1.1 MEANING & CORE IDEA
------------------------------------------------------------------------
Virtualization makes one physical resource appear as many logical resources
(or many physical resources appear as one). In cloud computing, the most common
form is server virtualization: one host runs many VMs.


------------------------------------------------------------------------
1.2 WHY VIRTUALIZATION WAS NEEDED
------------------------------------------------------------------------
SUBTOPICS:
  a) Low utilization of traditional servers (often 10–20% CPU historically)
  b) High CapEx and power/cooling costs for many underused machines
  c) Slow provisioning of new environments
  d) Difficulty isolating apps on shared OS without VMs

IMPORTANT FACTORS:
  • Better ROI on hardware
  • Faster environment creation for Dev/Test/Prod
  • Enables cloud multi-tenant IaaS


------------------------------------------------------------------------
1.3 VIRTUALIZATION vs TRADITIONAL PHYSICAL DEPLOYMENT
------------------------------------------------------------------------
Aspect            | Traditional Physical     | Virtualized
------------------|--------------------------|------------------------------
1 server : 1 OS   | Usually yes              | 1 server : many VMs/OSes
Provisioning      | Buy/install (slow)       | Create VM image (fast)
Utilization       | Often low                | Higher via consolidation
Isolation         | Physical separation      | Logical isolation via VMM
Scaling           | Buy more boxes           | Add VMs / migrate / cluster


------------------------------------------------------------------------
1.4 ROLE OF VIRTUALIZATION IN CLOUD COMPUTING
------------------------------------------------------------------------
IMPORTANT FACTORS:
  • Makes on-demand self-service possible (create VM in minutes)
  • Supports resource pooling and multi-tenancy
  • Enables elasticity (add/remove VM instances)
  • Allows live migration / maintenance with less downtime (when supported)

REAL-LIFE EXAMPLES:
  • Cloud providers run customer VMs on shared physical fleets
  • Syllabus practical: implement a VM on local machine using virtualization software


------------------------------------------------------------------------
1.5 EXAM TIP
------------------------------------------------------------------------
Define virtualization + why needed + role in cloud + 1 example. Mention
hypervisor as the key enabling software.

2. VIRTUALIZATION ARCHITECTURE  ★★
================================================================================

------------------------------------------------------------------------
2.1 HIGH-LEVEL ARCHITECTURE LAYERS
------------------------------------------------------------------------
  Applications (in Guest)
        ↑
  Guest Operating System
        ↑
  Virtual Hardware (vCPU, vRAM, vNIC, vDisk)
        ↑
  Hypervisor / VMM
        ↑
  Physical Hardware (CPU, Memory, Disk, NIC)
        ↑
  Data Center Facilities (power, cooling, racks)


------------------------------------------------------------------------
2.2 DETAILED COMPONENT VIEW
------------------------------------------------------------------------
SUBTOPICS:

1) PHYSICAL HARDWARE LAYER
   CPU, RAM, storage controllers, NICs, HBA, GPU (optional).

2) HYPERVISOR LAYER
   Schedules CPU, allocates memory, mediates I/O, enforces isolation.

3) VIRTUAL MACHINE LAYER
   Each VM has virtual devices + guest OS + apps.

4) MANAGEMENT LAYER
   VM lifecycle: create, start/stop, snapshot, clone, migrate, monitor.
   Examples: vCenter, cloud controllers, virt-manager, cloud consoles.

5) NETWORKING & STORAGE BACKENDS
   Virtual switches, storage arrays / local disks / networked storage.


------------------------------------------------------------------------
2.3 TYPE-1 vs TYPE-2 ARCHITECTURE  ★
------------------------------------------------------------------------

TYPE-1 (BARE-METAL) HYPERVISOR:
  • Runs directly on hardware
  • Host OS is minimal / not a full general-purpose OS in the usual sense
  • Higher performance; used in data centers and clouds
  EXAMPLES: VMware ESXi, Microsoft Hyper-V, Xen, KVM (kernel-based; often
  classed with Type-1 enterprise use)

TYPE-2 (HOSTED) HYPERVISOR:
  • Runs as an application on a conventional host OS (Windows/macOS/Linux)
  • Easier for desktops/labs; slightly more overhead
  EXAMPLES: Oracle VirtualBox, VMware Workstation/Player


------------------------------------------------------------------------
2.4 FULL VIRTUALIZATION vs PARA-VIRTUALIZATION vs HARDWARE-ASSISTED  ★
------------------------------------------------------------------------

A) FULL VIRTUALIZATION
   • Guest OS runs unmodified
   • Hypervisor traps & emulates sensitive instructions
   • Important factor: strong compatibility; historically more overhead
   • EXAMPLE: Running unmodified Windows guest on VMware/VirtualBox

B) PARA-VIRTUALIZATION
   • Guest OS is modified/aware of hypervisor (hypercalls)
   • Better performance for some operations by avoiding heavy traps
   • Important factor: needs para-virtual drivers / aware guest
   • EXAMPLE: Xen para-virtual guests; syllabus practical mentions para-virtualization

C) HARDWARE-ASSISTED VIRTUALIZATION
   • CPU features (Intel VT-x, AMD-V) help trap/emulate efficiently
   • Important factor: modern standard for full virtualization performance
   • EXAMPLE: Almost all modern cloud VMs rely on hardware virtualization extensions


------------------------------------------------------------------------
2.5 IMPORTANT ARCHITECTURAL FACTORS
------------------------------------------------------------------------
  • Isolation strength between VMs
  • Performance overhead of virtualization layer
  • Device virtualization method (emulation vs para-virtual drivers like virtio)
  • Manageability and tooling
  • Security of the hypervisor (attack surface)


------------------------------------------------------------------------
2.6 REAL-LIFE EXAMPLE
------------------------------------------------------------------------
A college lab PC (host OS Windows) runs VirtualBox (Type-2) to create a Linux
guest for networking experiments. In contrast, AWS/GCP data centers use Type-1
style hypervisors for thousands of customer VMs.

2.7 EXAM TIP
------------------------------------------------------------------------

4. APPLICATIONS OF VIRTUALIZATION  ★
================================================================================

------------------------------------------------------------------------
4.1 SERVER CONSOLIDATION
------------------------------------------------------------------------
Run multiple workloads on fewer physical servers.
IMPORTANT FACTORS: lower hardware, power, rack space costs.
EXAMPLE: 10 lightly used physical servers consolidated onto 2 strong hosts.


------------------------------------------------------------------------
4.2 DEVELOPMENT AND TESTING
------------------------------------------------------------------------
Create isolated environments quickly.
IMPORTANT FACTORS: reproducible labs; safe experiments.
EXAMPLE: Test software on Windows and Linux VMs without dual-boot.


------------------------------------------------------------------------
4.3 CLOUD COMPUTING / MULTI-TENANT IaaS
------------------------------------------------------------------------
Providers give each customer virtual servers on shared hardware.
IMPORTANT FACTORS: on-demand provisioning; billing by VM time.
EXAMPLE: Students create GCP/AWS VMs for assignments.


------------------------------------------------------------------------
4.4 DISASTER RECOVERY & BUSINESS CONTINUITY
------------------------------------------------------------------------
Replicate VMs to another site; restore faster than bare-metal rebuilds.
IMPORTANT FACTORS: RPO/RTO; VM image portability.
EXAMPLE: Nightly replication of critical VMs to a DR site.


------------------------------------------------------------------------
4.5 DESKTOP VIRTUALIZATION (VDI)
------------------------------------------------------------------------
User desktops run as VMs in data center; accessed via thin clients.
IMPORTANT FACTORS: centralized management; security of data in DC.
EXAMPLE: Call-center agents using virtual desktops.


------------------------------------------------------------------------
4.6 LEGACY APPLICATION SUPPORT
------------------------------------------------------------------------
Keep old OS/apps running as VMs on modern hardware.
IMPORTANT FACTORS: hardware abstraction reduces dependency on old servers.
EXAMPLE: Old accounting software needing Windows Server 2008 runs in a VM.


------------------------------------------------------------------------
4.7 SECURITY SANDBOXING / ISOLATION
------------------------------------------------------------------------
Malware analysis or untrusted code in isolated VMs.
IMPORTANT FACTORS: containment; snapshot rollback.
EXAMPLE: Security student analyzes malware inside an isolated VM.


------------------------------------------------------------------------
4.8 TRAINING & EDUCATION
------------------------------------------------------------------------
Each learner gets identical VM labs.
IMPORTANT FACTORS: reset to clean snapshot after class.
EXAMPLE: CC-I practical — create a VM on local machine.

6. CPU VIRTUALIZATION  ★★
================================================================================

------------------------------------------------------------------------
6.1 DEFINITION
------------------------------------------------------------------------
CPU virtualization allows multiple virtual CPUs (vCPUs) across VMs to share
physical CPU cores safely and efficiently under hypervisor control.


------------------------------------------------------------------------
6.2 HOW IT WORKS (CONCEPTUAL)
------------------------------------------------------------------------
SUBTOPICS:
  a) Time-slicing / scheduling physical CPU among vCPUs
  b) Trap-and-emulate for privileged instructions
  c) Hardware assistance (VT-x / AMD-V) for efficient transitions
  d) CPU modes: root mode (hypervisor) vs non-root mode (guest) in hardware-assisted designs


------------------------------------------------------------------------
6.3 TECHNIQUES
------------------------------------------------------------------------

1) SOFTWARE EMULATION / BINARY TRANSLATION (HISTORICAL / SPECIAL CASES)
   Sensitive instructions translated or trapped without guest modification.

2) PARA-VIRTUALIZED CPU INTERFACE
   Guest cooperates via hypercalls for privileged operations.

3) HARDWARE-ASSISTED CPU VIRTUALIZATION (MODERN DEFAULT)
   CPU extensions reduce overhead of running unmodified guests.


------------------------------------------------------------------------
6.4 IMPORTANT FACTORS
------------------------------------------------------------------------
  • Number of vCPUs vs physical cores (avoid extreme overcommit for latency-sensitive apps)
  • CPU affinity / NUMA awareness on large hosts
  • Steal time: guest ready but waiting for real CPU (contention signal)
  • Features exposed to guest (CPU flags) affect app compatibility


------------------------------------------------------------------------
6.5 BENEFITS
------------------------------------------------------------------------
  • Multiple OS instances share one CPU package
  • Better utilization of expensive processors
  • Flexible resizing of VM compute capacity


------------------------------------------------------------------------
6.6 CHALLENGES
------------------------------------------------------------------------
  • Noisy neighbor: one VM’s CPU spike slows others
  • Overhead of world switches (hypervisor ↔ guest)
  • Licensing/OS limits on vCPU topology in some products


------------------------------------------------------------------------
6.7 REAL-LIFE EXAMPLES
------------------------------------------------------------------------
  • Creating a VM with 2 vCPUs for a web app and 8 vCPUs for a build server on
    the same host
  • Cloud instance types (e.g., 2 vCPU / 4 GB) map to scheduled shares of host CPUs
  • Online exam portal scales out more vCPU-backed instances during peak login


------------------------------------------------------------------------
6.8 EXAM TIP
------------------------------------------------------------------------
Definition + hardware-assisted vs para vs full + scheduling/sharing idea +
2 factors (overcommit, noisy neighbor) + example.

7. NETWORK VIRTUALIZATION  ★★
================================================================================

------------------------------------------------------------------------
7.1 DEFINITION
------------------------------------------------------------------------
Network virtualization abstracts physical network resources to create multiple
logical networks (virtual networks, virtual switches, virtual NICs) that are
decoupled from the underlying cables and switches.


------------------------------------------------------------------------
7.2 KEY BUILDING BLOCKS
------------------------------------------------------------------------
SUBTOPICS:
  a) vNIC — virtual network interface card attached to a VM
  b) Virtual Switch (vSwitch) — software switch on the host connecting VMs
  c) VLAN / VXLAN / overlay networks — isolate and scale logical networks
  d) Virtual Router / Gateway — interconnects virtual subnets
  e) Firewall / Security Groups — virtualized packet filtering rules
  f) Load balancer (virtual) — distributes traffic across VM instances
  g) SDN (Software-Defined Networking) — centralized programmable control plane


------------------------------------------------------------------------
7.3 HOW VM TRAFFIC FLOWS (SIMPLE)
------------------------------------------------------------------------
  VM-A (vNIC) → Virtual Switch on Host → Physical NIC → Physical Network
                      ↕
                 VM-B (same host may switch locally without leaving host)


------------------------------------------------------------------------
7.4 IMPORTANT FACTORS
------------------------------------------------------------------------
  • Isolation between tenants (critical in cloud)
  • Bandwidth sharing / QoS / traffic shaping
  • Latency overhead of virtual switching
  • Security: micro-segmentation, security groups
  • IP addressing, DHCP, DNS in virtual networks
  • Hybrid connectivity (VPN / interconnect to on-prem)


------------------------------------------------------------------------
7.5 BENEFITS
------------------------------------------------------------------------
  • Rapid creation of isolated networks without recabling
  • Multi-tenant separation on shared fabric
  • Programmable policies (infrastructure as software)
  • Supports elastic cloud networking (VPC/VNet)


------------------------------------------------------------------------
7.6 CHALLENGES
------------------------------------------------------------------------
  • Complexity of overlays and troubleshooting
  • Misconfigured security groups causing outages or exposures
  • Performance overhead if not using accelerated networking


------------------------------------------------------------------------
7.7 REAL-LIFE EXAMPLES
------------------------------------------------------------------------
  • AWS VPC / Azure VNet / GCP VPC with subnets and firewall rules
  • Two student project VMs talking on a private virtual network
  • Micro-segmentation: only web VMs can reach DB VMs on port 3306


------------------------------------------------------------------------
7.8 EXAM TIP
------------------------------------------------------------------------
Define + list vNIC/vSwitch/VLAN/security groups + draw simple VM→vSwitch→NIC
flow + give VPC example.

8. STORAGE VIRTUALIZATION  ★★
================================================================================

------------------------------------------------------------------------
8.1 DEFINITION
------------------------------------------------------------------------
Storage virtualization abstracts physical storage devices into logical storage
pools that can be allocated to VMs as virtual disks, volumes, or file shares,
independent of the exact physical disks underneath.


------------------------------------------------------------------------
8.2 FORMS OF STORAGE VIRTUALIZATION
------------------------------------------------------------------------
SUBTOPICS:

1) BLOCK STORAGE VIRTUALIZATION
   Virtual disks (vDisk / EBS-like volumes) appear as block devices to guest OS.
   EXAMPLE: Attaching a 50 GB virtual disk to a VM.

2) FILE STORAGE VIRTUALIZATION
   Shared file systems presented over NFS/SMB to many clients/VMs.
   EXAMPLE: Shared project drive mounted by multiple lab VMs.

3) OBJECT STORAGE (CLOUD-ORIENTED)
   Objects accessed via API (not a classic local disk), often used beside VMs.
   EXAMPLE: Screenshots stored in S3 / Cloud Storage buckets.

4) ARRAY-BASED / CONTROLLER-BASED VIRTUALIZATION
   Storage arrays pool many disks (RAID/LUN virtualization).

5) SOFTWARE-DEFINED STORAGE (SDS)
   Storage services managed by software across commodity disks/nodes.


------------------------------------------------------------------------
8.3 VM DISK CONCEPTS
------------------------------------------------------------------------
  • Virtual Disk Files (e.g., VMDK, VHD/VHDX, QCOW2)
  • Thin provisioning — allocate on write; saves space
  • Thick provisioning — pre-allocate space for predictable performance
  • Snapshots / clones of virtual disks
  • Persistence types: persistent vs temporary disks (cloud)


------------------------------------------------------------------------
8.4 IMPORTANT FACTORS
------------------------------------------------------------------------
  • IOPS and throughput limits
  • Latency (local SSD vs network storage)
  • Redundancy (RAID, replication, erasure coding)
  • Thin provisioning risks (datastore overfill)
  • Backup/snapshot consistency (especially databases)
  • Encryption at rest


------------------------------------------------------------------------
8.5 BENEFITS
------------------------------------------------------------------------
  • Flexible resizing of disks
  • Better utilization via pooling
  • Easier migration of VM storage
  • Supports templates and rapid clones


------------------------------------------------------------------------
8.6 CHALLENGES
------------------------------------------------------------------------
  • Storage contention (noisy neighbor on shared arrays)
  • Snapshot sprawl consuming space
  • Complexity of multipathing and zoning in SAN environments


------------------------------------------------------------------------
8.7 REAL-LIFE EXAMPLES
------------------------------------------------------------------------
  • Expanding a VM’s disk when student project data grows
  • Cloud block volume attached to Compute Engine / EC2
  • Taking a disk snapshot before OS upgrade


------------------------------------------------------------------------
8.8 EXAM TIP
------------------------------------------------------------------------
Definition + block vs file (+ object mention) + thin vs thick + 3 important
factors (IOPS, redundancy, snapshots) + example.

9. VIRTUAL INFRASTRUCTURES  ★★
================================================================================

------------------------------------------------------------------------
9.1 DEFINITION
------------------------------------------------------------------------
A virtual infrastructure is the complete set of virtualized compute, storage,
and network resources — managed as a software-defined data center fabric —
on which applications and VMs run.


------------------------------------------------------------------------
9.2 COMPONENTS OF A VIRTUAL INFRASTRUCTURE
------------------------------------------------------------------------
  • Virtual compute pool (clusters of hypervisor hosts)
  • Virtual networking (vSwitches, routers, firewalls, load balancers)
  • Virtual storage pools / datastores
  • Management & orchestration plane
  • Templates, catalogs, and policy engines
  • Monitoring, logging, and identity integration


------------------------------------------------------------------------
9.3 CHARACTERISTICS
------------------------------------------------------------------------
IMPORTANT FACTORS:
  • Resource pooling across hosts
  • Policy-based placement of VMs
  • Elasticity: grow/shrink VM counts
  • Abstraction from hardware vendors (to a degree)
  • API-driven automation (cloud style)


------------------------------------------------------------------------
9.4 VIRTUAL INFRASTRUCTURE vs PHYSICAL INFRASTRUCTURE
------------------------------------------------------------------------
Physical: buy servers, cables, arrays; change is slow and hardware-bound.
Virtual: define networks/disks/VMs in software; change is faster and repeatable.


------------------------------------------------------------------------
9.5 REAL-LIFE EXAMPLES
------------------------------------------------------------------------
  • VMware vSphere cluster used as enterprise private-cloud foundation
  • OpenStack deployment providing virtual infra APIs
  • Public cloud account: VMs + VPC + disks = rented virtual infrastructure


------------------------------------------------------------------------
9.6 EXAM TIP
------------------------------------------------------------------------

physical + one private and one public example.

10. ANATOMY OF CLOUD INFRASTRUCTURE  ★★
================================================================================

“Anatomy” means the internal structural parts of cloud infrastructure and how
they fit together — from facilities up to customer-facing virtual resources.

------------------------------------------------------------------------
10.1 LAYERED ANATOMY (BOTTOM → TOP)
------------------------------------------------------------------------

1) FACILITY LAYER
   Building, power (UPS/generators), cooling, fire suppression, physical security.
   IMPORTANT FACTORS: uptime depends on power/cooling redundancy.
   EXAMPLE: Tiered data-center facility standards.

2) PHYSICAL COMPUTE & STORAGE HARDWARE
   Server racks, CPU/RAM nodes, flash/HDD arrays, GPUs.
   EXAMPLE: Blade/rack servers in cloud regions.

3) PHYSICAL NETWORK FABRIC
   Top-of-rack switches, aggregation/core, backbone links, peering to Internet.
   EXAMPLE: High-speed DC network connecting racks.

4) VIRTUALIZATION LAYER
   Hypervisors on hosts; clustering; virtual networking/storage abstractions.
   EXAMPLE: Host fleet running customer VMs.

5) CLOUD CONTROL PLANE (MANAGEMENT)
   APIs, schedulers, image services, billing, monitoring, IAM.
   IMPORTANT FACTORS: this is how “create VM” requests become reality.
   EXAMPLE: Cloud console / API calling internal orchestrators.

6) VIRTUAL RESOURCE LAYER (TENANT VIEW)
   VMs, virtual disks, virtual networks, load balancers, IPs.
   EXAMPLE: Student’s GCE VM + disk + VPC firewall rules.

7) PLATFORM & APPLICATION SERVICES (OPTIONAL UPPER LAYERS)
   Managed DB, PaaS, SaaS built on the same foundation.
   EXAMPLE: Cloud SQL running on provider-managed virtual infra.


------------------------------------------------------------------------
10.2 ANATOMY OF A SINGLE CLOUD VM (TENANT PERSPECTIVE)
------------------------------------------------------------------------
  • Identity & permissions (who can create/start it)
  • Machine image (OS template)
  • vCPU / memory shape
  • Boot disk + optional data disks
  • vNIC attached to virtual network/subnet
  • Public/private IP, firewall rules
  • Metadata / startup scripts
  • Monitoring agents and logs


------------------------------------------------------------------------
10.3 REGIONS, ZONES, AND FAILURE DOMAINS
------------------------------------------------------------------------
SUBTOPICS:
  • Region — geographic area
  • Zone / Availability Zone — isolated failure domain inside a region
IMPORTANT FACTORS:
  • Spread replicas across zones for high availability
  • Choose region for latency and data residency


------------------------------------------------------------------------
10.4 IMPORTANT FACTORS IN CLOUD INFRASTRUCTURE DESIGN
------------------------------------------------------------------------
  • Scalability of control plane and data plane
  • Multi-tenant isolation (compute/network/storage)
  • Hardware failure tolerance
  • Security (physical + hypervisor + network)
  • Observability and automated healing
  • Energy efficiency / density


------------------------------------------------------------------------
10.5 REAL-LIFE END-TO-END EXAMPLE
------------------------------------------------------------------------
You click “Create Linux VM” in GCP:
  1. IAM checks permission
  2. Control plane schedules VM onto a host in selected zone
  3. Hypervisor starts guest from image on virtualized CPU/RAM
  4. Virtual disk attaches from storage system
  5. vNIC connects to VPC network with firewall rules
  6. Metering starts for billing
This is cloud infrastructure anatomy in action.


------------------------------------------------------------------------
10.6 EXAM TIP
------------------------------------------------------------------------
Write layered anatomy (facility → hardware → network → virtualization → control
plane → tenant virtual resources) + VM anatomy bullets + region/zone note.

11. VIRTUAL CLUSTERING  ★★
================================================================================

------------------------------------------------------------------------
11.1 DEFINITION
------------------------------------------------------------------------
Virtual clustering is the grouping of multiple virtualized hosts (and/or VMs)
into a coordinated cluster so that workloads can run with higher availability,
load distribution, and easier management — using virtualization features such as
shared storage, VM migration, and failover.


------------------------------------------------------------------------
11.2 WHY CLUSTERING IS NEEDED IN VIRTUAL ENVIRONMENTS
------------------------------------------------------------------------
  • Single host failure should not kill all services
  • Balance VMs across hosts for performance
  • Enable maintenance (evacuate VMs, patch host)
  • Scale out capacity by adding hosts


------------------------------------------------------------------------
11.3 SUBTOPICS / CLUSTER CAPABILITIES
------------------------------------------------------------------------

1) HIGH AVAILABILITY (HA)
   If a host fails, VMs restart on another host in the cluster.
   IMPORTANT FACTORS: needs cluster membership + shared storage or equivalent
   restart capability.

2) LOAD BALANCING / DISTRIBUTED RESOURCE SCHEDULING
   Place or move VMs to hosts with free CPU/RAM.
   EXAMPLE: VMware DRS-like behavior; cloud schedulers placing instances.

3) LIVE MIGRATION (vMOTION-STYLE)
   Move a running VM between hosts with minimal downtime.
   IMPORTANT FACTORS: shared or mirrored storage; compatible CPUs; good network.

4) SHARED STORAGE FOR CLUSTER
   Datastores accessible by all hosts so any host can run the VM disks.

5) FAULT TOLERANCE (ADVANCED)
   Lockstep secondary VM for near-zero downtime (specialized/expensive).

6) VM-LEVEL CLUSTERS (APPLICATION CLUSTERING)
   Multiple VMs form an app cluster (e.g., web tier behind load balancer),
   separate from hypervisor host clustering — but often used together.


------------------------------------------------------------------------
11.4 VIRTUAL CLUSTER vs PHYSICAL CLUSTER
------------------------------------------------------------------------
Physical cluster: clustered OS/app nodes on physical machines.
Virtual cluster: clustering applied in virtualized layer (hosts/VMs), giving
faster provisioning and hardware independence, while still needing good design
for shared storage/network quorum.


------------------------------------------------------------------------
11.5 IMPORTANT FACTORS
------------------------------------------------------------------------
  • Quorum / split-brain prevention in host clusters
  • Network reliability between hosts
  • Shared storage performance
  • Compatibility for live migration
  • Capacity headroom for failover (N+1 thinking)
  • Licensing and management complexity


------------------------------------------------------------------------
11.6 BENEFITS
------------------------------------------------------------------------
  • Higher availability
  • Easier maintenance windows
  • Better resource utilization across hosts
  • Foundation for private cloud / virtual infrastructure


------------------------------------------------------------------------
11.7 CHALLENGES
------------------------------------------------------------------------
  • Cluster misconfiguration risk
  • Storage becoming a single point of failure if poorly designed
  • Live migration failures under heavy load


------------------------------------------------------------------------
11.8 REAL-LIFE EXAMPLES
------------------------------------------------------------------------
  • VMware HA cluster of ESXi hosts in a college data center
  • Cloud managed instance groups + autoscaling across zones (cluster-like elasticity)
  • Failover of a critical VM when one hypervisor host loses power


------------------------------------------------------------------------
11.9 EXAM TIP
------------------------------------------------------------------------
Definition + HA + load distribution + live migration + shared storage + benefits/
challenges + example. Mention that clustering supports cloud reliability.


================================================================================
12. BENEFITS, CHALLENGES & BEST PRACTICES
================================================================================

------------------------------------------------------------------------
12.1 BENEFITS OF VIRTUALIZATION (SUMMARY)
------------------------------------------------------------------------
  • Higher hardware utilization / consolidation
  • Faster provisioning and cloning
  • Isolation between workloads
  • Easier backup/DR via VM images/snapshots
  • Enables cloud multi-tenancy and elasticity
  • Reduced physical footprint and often energy savings


------------------------------------------------------------------------
12.2 CHALLENGES / RISKS
------------------------------------------------------------------------
  • Hypervisor is a critical security target
  • Resource contention (CPU, disk I/O, network)
  • VM sprawl (too many forgotten VMs)
  • Licensing complexity
  • Performance overhead (usually small today, but not zero)
  • Management complexity at scale


------------------------------------------------------------------------
12.3 BEST PRACTICES (SHORT, EXAM + PRACTICAL)
------------------------------------------------------------------------
  • Right-size vCPU/RAM; shut down idle VMs
  • Use templates for consistency
  • Patch hypervisors and guest OS regularly
  • Segment networks; least-privilege access
  • Monitor steal time / IOPS latency / host capacity
  • Plan cluster failover capacity
  • Snapshots ≠ backups; keep proper backup policy

------------------------------------------------------------------------
13.1 MUST-MEMORIZE DEFINITIONS
------------------------------------------------------------------------
• Virtualization — logical resources over physical hardware; many isolated envs
• Hypervisor/VMM — software managing VMs on hardware
• Type-1 — bare-metal hypervisor; Type-2 — hosted on OS
• CPU virtualization — sharing physical CPUs among vCPUs
• Network virtualization — logical networks over physical fabric
• Storage virtualization — logical storage pools/volumes over physical disks
• Virtual infrastructure — pooled virtual compute + network + storage + management
• Virtual clustering — coordinated hosts/VMs for HA, balancing, migration


------------------------------------------------------------------------
13.2 MUST-MEMORIZE LISTS
------------------------------------------------------------------------
Virtualization architecture layers:
  Apps → Guest OS → Virtual hardware → Hypervisor → Physical hardware

Approaches:
  Full / Para / Hardware-assisted virtualization

Syllabus resource virtualizations:
  CPU, Network, Storage (+ server/machine virtualization overall)

Cloud infrastructure anatomy:
  Facility → Hardware → Network → Virtualization → Control plane → Tenant resources

Cluster features:
  HA, load balancing/DRS, live migration, shared storage


------------------------------------------------------------------------
13.3 CONFUSING PAIRS
------------------------------------------------------------------------
Type-1 vs Type-2:
  Type-1 on hardware (DC/cloud); Type-2 on host OS (desktop/labs).

Full vs Para-virtualization:
  Full = unmodified guest; Para = guest aware/modified for hypercalls.

Virtual host cluster vs VM application cluster:
  Host cluster protects/manages VM placement; app cluster is multiple VMs
  cooperating at software level (e.g., web farm).

Storage virtualization vs cloud storage service:
  Virtualization is abstraction technology; cloud storage is a delivered service
  (often built using virtualization/SDS underneath).

------------------------------------------------------------------------
• Hypervisor Types: “1 is on the iron; 2 is on the OS”
• Anatomy stack: FHVCT → Facility, Hardware, (network), Virtualization,
  Control plane, Tenant view
• Cluster keywords: HA + Migrate + Balance + Shared storage
