0. BASIC TERMINOLOGIES (FOUNDATION)
================================================================================

------------------------------------------------------------------------
0.1 CLOUD SERVICE MODEL
------------------------------------------------------------------------
DEFINITION:
  A classification of cloud offerings based on WHAT the provider manages and
  WHAT the customer manages (control vs convenience trade-off).

IMPORTANT FACTORS:
  • Defines responsibility split
  • Affects cost, flexibility, and skill requirements
  • Main models: IaaS, PaaS, SaaS (SPI stack)

REAL-LIFE EXAMPLES:
  • IaaS: renting a virtual machine
  • PaaS: deploying code on a managed app platform
  • SaaS: using Gmail without installing mail servers


------------------------------------------------------------------------
0.2 CLOUD DEPLOYMENT MODEL (TYPE OF CLOUD)
------------------------------------------------------------------------
DEFINITION:
  Classification based on WHERE cloud infrastructure is hosted and WHO can use it
  (ownership, access, and tenancy pattern).

IMPORTANT FACTORS:
  • Public / Private / Hybrid / Community
  • Affects security, cost, compliance, and control

REAL-LIFE EXAMPLES:
  • Public: AWS / GCP / Azure shared cloud
  • Private: bank's internal cloud
  • Hybrid: hospital keeps patient DB private, uses public cloud for website


------------------------------------------------------------------------
0.3 SPI STACK
------------------------------------------------------------------------
DEFINITION:
  SPI = Software (SaaS) + Platform (PaaS) + Infrastructure (IaaS) — the three
  classical cloud service models stacked from application down to infrastructure.

IMPORTANT FACTORS:
  • Moving UP the stack = more managed by provider, less control by customer
  • Moving DOWN the stack = more control, more management responsibility


------------------------------------------------------------------------
0.4 SHARED RESPONSIBILITY MODEL
------------------------------------------------------------------------
DEFINITION:
  Security/operations duties are split: provider secures the cloud; customer
  secures what they put in the cloud (and their configurations).

IMPORTANT FACTORS:
  • Exact split depends on IaaS vs PaaS vs SaaS
  • Misunderstanding this causes exam and real-world mistakes

REAL-LIFE EXAMPLE:
  In IaaS, provider secures hardware; you must patch the guest OS.
  In SaaS (Gmail), provider patches almost everything; you manage user access.


------------------------------------------------------------------------
0.5 MULTI-TENANCY
------------------------------------------------------------------------
DEFINITION:
  Multiple customers (tenants) share the same physical resources with logical
  isolation of data and workloads.

IMPORTANT FACTORS:
  • Improves cost efficiency
  • Requires strong isolation and access control

REAL-LIFE EXAMPLE:
  Thousands of companies using Salesforce on shared platform infrastructure.


------------------------------------------------------------------------
0.6 CLOUD ARCHITECTURE
------------------------------------------------------------------------
DEFINITION:
  The structural design of cloud systems — front-end, back-end, network, and
  management/security layers — and how they interact.


------------------------------------------------------------------------
0.7 REFERENCE MODEL
------------------------------------------------------------------------
DEFINITION:
  A conceptual layered model that standardizes how cloud roles, services, and
  layers relate (helps compare providers and design systems consistently).

1. OVERVIEW — TYPES OF CLOUD & CLOUD COMPUTING MODELS  ★
================================================================================

------------------------------------------------------------------------
1.1 WHAT “CLOUD COMPUTING MODELS” MEANS
------------------------------------------------------------------------
Cloud computing models answer three exam-critical questions:

  1) HOW is the service delivered?     → Service models (IaaS / PaaS / SaaS / others)
  2) WHERE is it deployed / who uses it? → Deployment models (Public / Private /
                                           Hybrid / Community)
  3) HOW is it structured internally?  → Architecture + Reference model

Together, these models explain cloud from business, technical, and design views.


------------------------------------------------------------------------
1.2 TWO PRIMARY CLASSIFICATIONS (MEMORIZE)
------------------------------------------------------------------------
A) SERVICE MODELS (based on service offered / management level)
   IaaS, PaaS, SaaS (+ other XaaS services)

B) DEPLOYMENT MODELS / TYPES OF CLOUD (based on ownership & access)
   Public, Private, Hybrid, Community


------------------------------------------------------------------------
1.3 WHY MODELS MATTER
------------------------------------------------------------------------
IMPORTANT FACTORS:
  • Correct model choice balances cost, control, security, and speed
  • Wrong model causes overspending, lock-in, or compliance failure
  • Exams often ask differences, responsibility split, and use-case selection

REAL-LIFE EXAMPLE:
  A student project needs a quick web app → PaaS/SaaS is faster than building
  everything on raw IaaS VMs.


------------------------------------------------------------------------
1.4 EXAM TIP
------------------------------------------------------------------------
Start Unit 2 answers by stating: “Cloud models are classified mainly into service
models and deployment models.” Then expand the asked part.

2. CLOUD SERVICE MODELS (SPI STACK)  ★★
================================================================================

------------------------------------------------------------------------
2.1 DEFINITION
------------------------------------------------------------------------
Cloud service models describe the category of capability delivered over the cloud
and the division of management responsibilities between provider and customer.


------------------------------------------------------------------------
2.2 THE SPI STACK (BOTTOM → TOP)
------------------------------------------------------------------------
  Layer (bottom)  Infrastructure as a Service (IaaS)
       ↑
  Layer (middle)  Platform as a Service (PaaS)
       ↑
  Layer (top)     Software as a Service (SaaS)

Pizza analogy (popular exam memory aid):
  • IaaS  = You cook at home using rented kitchen equipment
  • PaaS  = Take-and-bake: oven + ingredients partly prepared
  • SaaS  = Restaurant dining: finished meal served to you


------------------------------------------------------------------------
2.3 CONTROL vs CONVENIENCE TRADE-OFF
------------------------------------------------------------------------
  More customer control ←  IaaS  —  PaaS  —  SaaS  → More provider management
  More ops responsibility ← IaaS  —  PaaS  —  SaaS  → Less ops for customer
  Higher flexibility      ← IaaS  —  PaaS  —  SaaS  → Faster ready-to-use apps


------------------------------------------------------------------------
2.4 IMPORTANT FACTORS (COMMON TO ALL SERVICE MODELS)
------------------------------------------------------------------------
  • Who manages OS, runtime, app, data, identity?
  • Skill level required from customer team
  • Speed of deployment
  • Customization depth
  • Vendor lock-in risk
  • Pricing pattern (VM-hours vs app hosting vs per-user subscription)


------------------------------------------------------------------------
2.5 EXAM TIP
------------------------------------------------------------------------
Whenever comparing models, draw a responsibility table (Provider vs Customer)
for Hardware, Virtualization, OS, Runtime, Application, Data.

3. INFRASTRUCTURE AS A SERVICE (IaaS)  ★★
================================================================================

------------------------------------------------------------------------
3.1 DEFINITION
------------------------------------------------------------------------
IaaS provides fundamental computing resources — virtual machines, storage,
networks, and related infrastructure — over the Internet. Customers rent
infrastructure instead of buying physical servers.


------------------------------------------------------------------------
3.2 WHAT PROVIDER MANAGES vs CUSTOMER MANAGES
------------------------------------------------------------------------
PROVIDER TYPICALLY MANAGES:
  • Physical data center, power, cooling
  • Physical servers, storage, networking gear
  • Virtualization / hypervisor layer

CUSTOMER TYPICALLY MANAGES:
  • Guest operating system (patching, hardening)
  • Middleware and runtimes
  • Applications and data
  • Network configs inside the VNet/VPC (security groups, etc.)
  • Identity and access for their resources


------------------------------------------------------------------------
3.3 SUBTOPICS / CAPABILITIES
------------------------------------------------------------------------
  a) Compute — VMs, bare-metal instances, auto-scaling groups
  b) Storage — block volumes, object storage, file storage, snapshots
  c) Networking — VPC/VNet, subnets, firewalls, load balancers, VPN/peering
  d) Complementary services — images, templates, monitoring agents


------------------------------------------------------------------------
3.4 IMPORTANT FACTORS
------------------------------------------------------------------------
  • Maximum flexibility among SPI models
  • Requires stronger admin skills (OS + networking + security)
  • Ideal for lift-and-shift migrations
  • Customer responsible for much of security configuration
  • Cost depends on instance size, hours running, storage, egress


------------------------------------------------------------------------
3.5 ADVANTAGES
------------------------------------------------------------------------
  • Full control over OS and stack
  • Rapid provisioning of servers
  • Pay only for used infrastructure
  • Good for custom / legacy apps that need special OS setup


------------------------------------------------------------------------
3.6 LIMITATIONS / CHALLENGES
------------------------------------------------------------------------
  • More management overhead than PaaS/SaaS
  • Misconfigured security can expose systems
  • Idle VMs waste money if not stopped
  • Patching and backups are customer duties (unless using managed add-ons)


------------------------------------------------------------------------
3.7 USE CASES
------------------------------------------------------------------------
  • Hosting websites/web apps on VMs
  • Dev/test environments
  • High-performance compute clusters
  • Backup and disaster recovery infrastructure
  • Lift-and-shift of on-prem servers


------------------------------------------------------------------------
3.8 REAL-LIFE EXAMPLES
------------------------------------------------------------------------
  • AWS EC2, Google Compute Engine, Azure Virtual Machines
  • Student starts a Linux VM on GCP for a practical lab
  • Company moves on-prem file server workload to cloud VMs


------------------------------------------------------------------------
3.9 EXAM TIP
------------------------------------------------------------------------
Definition + responsibility split + 3 advantages + 2 limitations + 2 examples
+ 1 use case = complete IaaS answer.

4. PLATFORM AS A SERVICE (PaaS)  ★★
================================================================================

------------------------------------------------------------------------
4.1 DEFINITION
------------------------------------------------------------------------
PaaS provides a ready platform (runtime, OS, middleware, development/deployment
tools) so developers can build, test, and deploy applications without managing
underlying servers.


------------------------------------------------------------------------
4.2 WHAT PROVIDER MANAGES vs CUSTOMER MANAGES
------------------------------------------------------------------------
PROVIDER TYPICALLY MANAGES:
  • Hardware, virtualization
  • OS, runtime, middleware, many platform services
  • Platform scaling, patching of managed layers

CUSTOMER TYPICALLY MANAGES:
  • Application code and configuration
  • Application data
  • User access to the application
  • Some environment settings / service bindings


------------------------------------------------------------------------
4.3 SUBTOPICS / CAPABILITIES
------------------------------------------------------------------------
  a) Application hosting / runtime (Java, Python, Node, etc.)
  b) Managed databases and caches (often offered as platform services)
  c) CI/CD and build/deploy pipelines
  d) Auto-scaling application instances
  e) Add-on services (queues, auth, logging)


------------------------------------------------------------------------
4.4 IMPORTANT FACTORS
------------------------------------------------------------------------
  • Speeds up development (focus on code, not servers)
  • Less OS-level control than IaaS
  • Platform constraints may limit exotic libraries/configs
  • Higher risk of platform lock-in if proprietary services are used heavily
  • Excellent for new cloud-native apps and student projects


------------------------------------------------------------------------
4.5 ADVANTAGES
------------------------------------------------------------------------
  • Faster time-to-market
  • Reduced ops burden
  • Built-in scaling and platform updates
  • Collaboration-friendly for development teams


------------------------------------------------------------------------
4.6 LIMITATIONS / CHALLENGES
------------------------------------------------------------------------
  • Less flexibility than IaaS
  • Possible vendor lock-in
  • Debugging may be harder when platform internals are hidden
  • Not ideal for apps needing custom kernel/OS modules


------------------------------------------------------------------------
4.7 USE CASES
------------------------------------------------------------------------
  • Web/mobile backend APIs
  • Microservices deployment
  • Data analytics apps on managed platforms
  • Rapid prototyping / hackathons


------------------------------------------------------------------------
4.8 REAL-LIFE EXAMPLES
------------------------------------------------------------------------
  • Google App Engine, AWS Elastic Beanstalk, Azure App Service
  • Heroku-style app platforms
  • Student deploys a Node.js API without configuring Linux packages manually


------------------------------------------------------------------------
4.9 EXAM TIP
------------------------------------------------------------------------
Emphasize: “PaaS = developers get platform; provider manages OS/runtime.”
Contrast with IaaS (you manage OS) and SaaS (you only use finished software).

5. SOFTWARE AS A SERVICE (SaaS)  ★★
================================================================================

------------------------------------------------------------------------
5.1 DEFINITION
------------------------------------------------------------------------
SaaS delivers ready-to-use software applications over the Internet, usually via
browser or app, on a subscription / per-user basis. Customers use the software;
they do not install or maintain the full stack.


------------------------------------------------------------------------
5.2 WHAT PROVIDER MANAGES vs CUSTOMER MANAGES
------------------------------------------------------------------------
PROVIDER TYPICALLY MANAGES:
  • Almost entire stack: hardware → OS → runtime → application
  • Availability, updates, most security patching of the app platform

CUSTOMER TYPICALLY MANAGES:
  • User accounts, roles, and access policies
  • Data they enter into the application
  • Endpoint devices and safe usage practices
  • Configuration options exposed by the vendor


------------------------------------------------------------------------
5.3 SUBTOPICS / DELIVERY CHARACTERISTICS
------------------------------------------------------------------------
  a) Multi-tenant application delivery
  b) Subscription billing (monthly/yearly/per seat)
  c) Automatic updates and feature rollouts
  d) Access via web/mobile with broad network access
  e) Integration via APIs with other business systems


------------------------------------------------------------------------
5.4 IMPORTANT FACTORS
------------------------------------------------------------------------
  • Fastest to adopt; lowest ops overhead
  • Limited deep customization
  • Data residency and privacy must be checked in contract/settings
  • Strong dependence on vendor uptime and roadmap
  • Ideal for standard business functions (email, CRM, office)


------------------------------------------------------------------------
5.5 ADVANTAGES
------------------------------------------------------------------------
  • No local install / no server maintenance for users
  • Anywhere access and easy collaboration
  • Predictable subscription pricing (often)
  • Quick onboarding for organizations and students


------------------------------------------------------------------------
5.6 LIMITATIONS / CHALLENGES
------------------------------------------------------------------------
  • Customization limits
  • Integration challenges with legacy systems
  • Data lock-in / export difficulties
  • Internet dependency
  • Compliance concerns for highly sensitive data


------------------------------------------------------------------------
5.7 USE CASES
------------------------------------------------------------------------
  • Email and office productivity
  • CRM / HR / accounting
  • Learning management systems
  • Collaboration and meetings


------------------------------------------------------------------------
5.8 REAL-LIFE EXAMPLES
------------------------------------------------------------------------
  • Gmail, Google Workspace, Microsoft 365
  • Salesforce, Zoho CRM, Slack, Zoom
  • College uses Google Classroom instead of hosting its own LMS servers


------------------------------------------------------------------------
5.9 EXAM TIP
------------------------------------------------------------------------
Always mention multi-tenancy + subscription + provider-managed application.
Give at least 3 concrete product examples.

6. COMPARISON OF IaaS, PaaS, SaaS  ★★ (VERY IMPORTANT)
================================================================================

------------------------------------------------------------------------
6.1 RESPONSIBILITY MATRIX (WRITE THIS IN EXAMS)
------------------------------------------------------------------------
Layer / Item        | IaaS        | PaaS         | SaaS
--------------------|-------------|--------------|-------------
Physical hardware   | Provider    | Provider     | Provider
Virtualization      | Provider    | Provider     | Provider
Operating System    | Customer    | Provider     | Provider
Runtime/Middleware  | Customer    | Provider     | Provider
Application         | Customer    | Customer     | Provider
Data                | Customer    | Customer     | Customer*
User Access Control | Customer    | Customer     | Shared/Customer

*In SaaS, customer owns/controls their content/data, while provider stores it.


------------------------------------------------------------------------
6.2 FEATURE COMPARISON
------------------------------------------------------------------------
Aspect              | IaaS                | PaaS                 | SaaS
--------------------|---------------------|----------------------|--------------------
Control             | Highest             | Medium               | Lowest
Ease of use         | Needs admin skills  | Developer-friendly   | End-user-friendly
Customization       | Very high           | Medium               | Limited
Time to start       | Moderate            | Fast                 | Fastest
Ops burden          | High                | Medium-Low           | Lowest
Typical user        | SysAdmin / DevOps   | Developers           | Business users
Example             | EC2 / GCE VMs       | App Engine / Beanstalk| Gmail / Salesforce


------------------------------------------------------------------------
6.3 REAL-LIFE COMBINED EXAMPLE (ONE BUSINESS USING ALL THREE)
------------------------------------------------------------------------
A retail startup:
  • SaaS: uses Gmail + Google Workspace for email/docs
  • PaaS: deploys order API on a managed app platform
  • IaaS: runs a special legacy inventory tool on a cloud VM

This shows models are complementary, not mutually exclusive.


------------------------------------------------------------------------
6.4 EXAM TIP
------------------------------------------------------------------------
Difference questions are common. Use a table + 1 example each + one line on
“control vs convenience.”

7. OTHER CLOUD SERVICES (BEYOND SPI)  ★
================================================================================

Besides IaaS/PaaS/SaaS, many “Anything as a Service (XaaS)” offerings exist.

------------------------------------------------------------------------
7.1 DATABASE AS A SERVICE (DBaaS)
------------------------------------------------------------------------
DEFINITION:
  Managed database engines where provider handles setup, patching, backups,
  replication options; customer focuses on schema/queries/data.

IMPORTANT FACTORS:
  • Reduces DBA operational load
  • Watch pricing for storage IOPS and replicas

REAL-LIFE EXAMPLES:
  • Amazon RDS, Cloud SQL (GCP), Azure SQL Database
  • Student project uses managed PostgreSQL instead of installing DB on VM


------------------------------------------------------------------------
7.2 FUNCTION AS A SERVICE / SERVERLESS (FaaS)
------------------------------------------------------------------------
DEFINITION:
  Run event-driven functions without managing servers; scale to zero when idle.

IMPORTANT FACTORS:
  • Pay per invocation/time
  • Cold starts; execution time limits
  • Great for automation and APIs with spiky traffic

REAL-LIFE EXAMPLES:
  • AWS Lambda, Google Cloud Functions, Azure Functions
  • Auto-create thumbnails when an image is uploaded to cloud storage


------------------------------------------------------------------------
7.3 STORAGE AS A SERVICE
------------------------------------------------------------------------
DEFINITION:
  On-demand storage (object/block/file) accessed over network APIs.

IMPORTANT FACTORS:
  • Durability classes / tiers (hot, cool, archive)
  • Data egress costs
  • Access control and encryption

REAL-LIFE EXAMPLES:
  • Amazon S3, Google Cloud Storage, Azure Blob Storage
  • Backing up project videos to object storage


------------------------------------------------------------------------
7.4 CONTAINER AS A SERVICE (CaaS)
------------------------------------------------------------------------
DEFINITION:
  Managed platform to run containers without building full cluster operations
  from scratch (or managed Kubernetes offerings).

IMPORTANT FACTORS:
  • Portability of container images
  • Orchestration, networking, and scaling still need design

REAL-LIFE EXAMPLES:
  • Google Kubernetes Engine (GKE), Amazon ECS/EKS, Azure AKS
  • Syllabus practical: build/deploy container app on GCP


------------------------------------------------------------------------
7.5 IDENTITY AS A SERVICE (IDaaS)
------------------------------------------------------------------------
DEFINITION:
  Cloud-hosted identity and access management (SSO, MFA, directory services).

IMPORTANT FACTORS:
  • Centralizes authentication
  • Critical for Zero Trust and least privilege

REAL-LIFE EXAMPLES:
  • Azure AD / Entra ID, Okta, Google Workspace identity


------------------------------------------------------------------------
7.6 DISASTER RECOVERY AS A SERVICE (DRaaS) & BACKUP AS A SERVICE
------------------------------------------------------------------------
DEFINITION:
  Cloud services that replicate / back up systems for recovery after failure.

IMPORTANT FACTORS:
  • RPO (how much data loss acceptable) and RTO (how fast restore needed)
  • Cross-region replication costs

REAL-LIFE EXAMPLE:
  College ERP nightly backups to another region for disaster recovery.


------------------------------------------------------------------------
7.7 SECURITY AS A SERVICE (SECaaS)
------------------------------------------------------------------------
DEFINITION:
  Security capabilities delivered via cloud (email filtering, CASB, managed SIEM).

IMPORTANT FACTORS:
  • Faster adoption of advanced security tooling
  • Still needs correct configuration and monitoring

REAL-LIFE EXAMPLE:
  Cloud email security filtering phishing before inbox delivery.


------------------------------------------------------------------------
7.8 NETWORK / CDN / MONITORING AS A SERVICE (SHORT NOTES)
------------------------------------------------------------------------
  • Networking services: VPC, DNS, VPN, load balancing
  • CDN: cached content delivery at edge (Cloud CDN, CloudFront)
  • Monitoring/Logging as a service: metrics, alerts, traces


------------------------------------------------------------------------
7.9 IMPORTANT FACTORS (XaaS OVERALL)
------------------------------------------------------------------------
  • Choose based on managed convenience vs control
  • Combine services (IaaS + DBaaS + FaaS) into architectures
  • Evaluate lock-in, pricing units, and SLAs per service


------------------------------------------------------------------------
7.10 EXAM TIP
------------------------------------------------------------------------
Write definition of XaaS + at least 5 other services with one-line meaning and
one example each. DBaaS, FaaS, Storage, CaaS, IDaaS are high-value picks.

8. CLOUD DEPLOYMENT MODELS (TYPES OF CLOUD)  ★★
================================================================================

Deployment models describe the cloud’s ownership, access scope, and operational
control. Syllabus phrase “Types of Cloud” mainly means these models.

------------------------------------------------------------------------
8.1 PUBLIC CLOUD
------------------------------------------------------------------------
DEFINITION:
  Cloud infrastructure owned and operated by a provider and available to the
  general public over the Internet (multi-tenant).

SUBTOPICS:
  • Shared resource pools
  • Self-service portals
  • Global regions and zones

IMPORTANT FACTORS:
  • Lowest entry cost; high elasticity
  • Less direct physical control
  • Must evaluate compliance/data residency

ADVANTAGES:
  • No CapEx for data center
  • Almost unlimited on-demand capacity
  • Fast setup

LIMITATIONS:
  • Shared environment concerns for some regulated data
  • Less customization of underlying facility
  • Internet dependency

REAL-LIFE EXAMPLES:
  • AWS, Microsoft Azure, Google Cloud Platform
  • Student using free-tier public cloud for labs


------------------------------------------------------------------------
8.2 PRIVATE CLOUD
------------------------------------------------------------------------
DEFINITION:
  Cloud infrastructure used exclusively by a single organization, managed
  internally or by a third party, on-premises or hosted.

SUBTOPICS:
  • On-prem private cloud
  • Hosted private cloud (dedicated)
  • Virtual private cloud concepts (logical isolation in public cloud — related idea)

IMPORTANT FACTORS:
  • Higher control and customization
  • Higher cost and admin overhead
  • Preferred for sensitive workloads

ADVANTAGES:
  • Stronger control over security/compliance
  • Dedicated resources possible
  • Custom policies and network design

LIMITATIONS:
  • Expensive to build/operate
  • Limited elasticity compared to hyperscale public cloud
  • Needs skilled internal team

REAL-LIFE EXAMPLES:
  • Bank’s internal private cloud for core banking modules
  • Large university private cloud for research data


------------------------------------------------------------------------
8.3 HYBRID CLOUD
------------------------------------------------------------------------
DEFINITION:
  Composition of two or more distinct clouds (usually private + public) that
  remain unique entities but are bound together for portability and orchestration.

SUBTOPICS:
  • Bursting to public cloud during peaks (cloud burst)
  • Sensitive data on private; scalable apps on public
  • Identity and network integration across environments

IMPORTANT FACTORS:
  • Flexibility to place each workload optimally
  • Complex integration, networking, and security
  • Needs consistent monitoring and governance

ADVANTAGES:
  • Balance of control and scalability
  • Cost optimization by workload placement
  • Better continuity options

LIMITATIONS:
  • Architectural complexity
  • Latency between environments
  • Skill and tooling requirements

REAL-LIFE EXAMPLES:
  • Hospital: patient records in private cloud; appointment website on public cloud
  • Retail: inventory system private; seasonal campaign site on public cloud


------------------------------------------------------------------------
8.4 COMMUNITY CLOUD
------------------------------------------------------------------------
DEFINITION:
  Cloud infrastructure shared by several organizations with common concerns
  (security, compliance, industry mission), managed internally or by a provider.

SUBTOPICS:
  • Industry consortia clouds
  • Government / education community clouds

IMPORTANT FACTORS:
  • Shared cost among members
  • Common compliance standards
  • Access limited to community members

ADVANTAGES:
  • Cost sharing with similar peers
  • Tailored controls for industry needs

LIMITATIONS:
  • Governance disagreements among members
  • Less global ecosystem than public hyperscalers

REAL-LIFE EXAMPLES:
  • Government departments sharing a community cloud
  • Universities collaborating on a research community cloud


------------------------------------------------------------------------
8.5 COMPARISON TABLE (EXAM FAVORITE)
------------------------------------------------------------------------
Model      | Who uses it              | Control | Cost     | Example focus
-----------|--------------------------|---------|----------|---------------------------
Public     | General public/orgs      | Low     | Low entry| Startups, students, SaaS
Private    | Single organization      | High    | High     | Banks, defense, sensitive
Hybrid     | Mix private + public     | Medium  | Medium   | Enterprises with mixed apps
Community  | Group with shared goals  | Medium  | Shared   | Govt/edu/industry groups


------------------------------------------------------------------------
8.6 IMPORTANT SELECTION FACTORS
------------------------------------------------------------------------
  • Data sensitivity and compliance
  • Budget and CapEx appetite
  • Need for extreme elasticity
  • Existing data-center investments
  • Integration complexity tolerance


------------------------------------------------------------------------
8.7 EXAM TIP
------------------------------------------------------------------------
Define all four models + table + one example each. For hybrid, mention cloud
bursting — examiners like that keyword.

9. CLOUD ARCHITECTURE  ★★
================================================================================

------------------------------------------------------------------------
9.1 DEFINITION
------------------------------------------------------------------------
Cloud architecture is the organized structure of components (client, network,
applications, services, runtime, storage, infrastructure, management, security)
that together deliver cloud services.


------------------------------------------------------------------------
9.2 FRONT END vs BACK END
------------------------------------------------------------------------
FRONT END (Client side):
  • Web browsers, mobile apps, thin/thick clients, CLI/SDK
  • User interface to access cloud services

BACK END (Provider side):
  • Application servers, services, storage, virtualization, physical hardware
  • Management, security, and metering systems

NETWORK:
  • Internet or private connectivity linking front end and back end


------------------------------------------------------------------------
9.3 MAJOR ARCHITECTURAL COMPONENTS / LAYERS
------------------------------------------------------------------------

1) CLIENT INFRASTRUCTURE
   Devices and software used by consumers to access cloud.
   EXAMPLE: Laptop browser accessing Google Drive.

2) APPLICATION
   Software delivered to the user (especially in SaaS).
   EXAMPLE: Gmail web application.

3) SERVICE
   Service catalog / capabilities offered (compute, storage, app services).
   EXAMPLE: “Create VM”, “Store object”, “Send email API”.

4) RUNTIME
   Execution environment for applications (managed runtimes in PaaS).
   EXAMPLE: Managed Node.js/Java runtime on App Engine.

5) STORAGE
   Data persistence systems (object/block/file/DB).
   EXAMPLE: Object storage for assignment PDFs.

6) INFRASTRUCTURE
   Compute, network, and foundational resources (often virtualized).
   EXAMPLE: VMs, virtual networks, load balancers.

7) MANAGEMENT
   Provisioning, monitoring, orchestration, billing, automation.
   EXAMPLE: Cloud console, autoscaler, logging dashboards.

8) SECURITY
   Identity, encryption, firewalls, compliance controls across layers.
   EXAMPLE: IAM roles, security groups, TLS certificates.

9) INTERNET / CONNECTIVITY
   Communication path between users and cloud resources.
   EXAMPLE: HTTPS access; VPN for hybrid connectivity.


------------------------------------------------------------------------
9.4 KEY ARCHITECTURAL PROPERTIES
------------------------------------------------------------------------
IMPORTANT FACTORS:
  • Scalability and elasticity mechanisms
  • High availability (multi-zone designs)
  • Loose coupling via APIs/services
  • Automation and observability
  • Security by design (defense in depth)
  • Multi-tenancy isolation


------------------------------------------------------------------------
9.5 SIMPLE ARCHITECTURE FLOW (EXAM DIAGRAM)
------------------------------------------------------------------------
  User Device (Front End)
        |  Internet / API
        v
  Entry: DNS + Load Balancer + Firewall
        |
        v
  Application / Service Layer
        |
        +--> Cache / CDN
        +--> App servers / Functions / Containers
        +--> Database / Object Storage
        |
        v
  Management + Monitoring + Billing
        |
        v
  Virtualization over Physical Data Center Resources


------------------------------------------------------------------------
9.6 REAL-LIFE EXAMPLE (E-COMMERCE ON CLOUD)
------------------------------------------------------------------------
  • Users open shopping website (front end)
  • Load balancer spreads traffic
  • App tier handles cart/orders
  • Managed DB stores orders; object storage stores product images
  • CDN caches images
  • Autoscaling adds app instances on sale day
  • IAM + HTTPS secure access; bills metered by usage


------------------------------------------------------------------------
9.7 EXAM TIP
------------------------------------------------------------------------
Draw front-end / back-end / network, list 7–9 components with one line each, and
explain one end-to-end example. Architecture questions reward diagrams.

10. CLOUD COMPUTING REFERENCE MODEL  ★★
================================================================================

------------------------------------------------------------------------
10.1 DEFINITION & PURPOSE
------------------------------------------------------------------------
A cloud computing reference model is a conceptual framework that describes cloud
layers, actors/roles, and service relationships in a standardized way.

WHY IT MATTERS:
  • Common vocabulary for students, architects, and vendors
  • Clarifies responsibilities across layers
  • Helps design interoperable and comparable cloud solutions
  • Useful for exam answers on “explain cloud reference model”


------------------------------------------------------------------------
10.2 TYPICAL LAYERED REFERENCE VIEW (BOTTOM → TOP)
------------------------------------------------------------------------
  1) PHYSICAL / FABRIC LAYER
     Servers, storage arrays, network devices, facilities.

  2) VIRTUAL INFRASTRUCTURE LAYER (IaaS-oriented)
     Hypervisors, VMs, virtual networks, virtual storage.

  3) PLATFORM LAYER (PaaS-oriented)
     OS/runtime abstractions, middleware, development/deployment services.

  4) APPLICATION LAYER (SaaS-oriented)
     End-user applications and business software.

  5) ACCESS / PRESENTATION LAYER
     Portals, APIs, mobile/web clients.

Cross-cutting layers (cut across all levels):
  • Security
  • Management & Monitoring
  • Governance / Compliance
  • Metering & Billing


------------------------------------------------------------------------
10.3 ACTORS / ROLES IN REFERENCE MODELS
------------------------------------------------------------------------
  • Cloud Consumer — uses cloud services
  • Cloud Provider — offers and operates services
  • Cloud Broker — manages use, performance, delivery across providers (optional)
  • Cloud Auditor — conducts independent assessments (security/compliance)
  • Cloud Carrier — provides connectivity transport between consumer & provider

IMPORTANT FACTORS:
  • Roles help assign accountability
  • In many student answers, Consumer + Provider are essential; others earn bonus


------------------------------------------------------------------------
10.4 MAPPING REFERENCE MODEL TO SPI
------------------------------------------------------------------------
  Application layer     ↔ SaaS
  Platform layer        ↔ PaaS
  Infrastructure layer  ↔ IaaS
  Physical layer        ↔ Data center fabric (provider owned in public cloud)


------------------------------------------------------------------------
10.5 IMPORTANT FACTORS
------------------------------------------------------------------------
  • Reference model is conceptual (not one vendor’s product diagram)
  • Real architectures instantiate these layers with concrete services
  • Security and management are cross-cutting, not ignored side topics
  • Helps decide where customization and responsibility sit


------------------------------------------------------------------------
10.6 REAL-LIFE MAPPING EXAMPLE
------------------------------------------------------------------------
Using Gmail (SaaS):
  • Consumer: student/teacher
  • Provider: Google
  • Access layer: browser/app
  • Application layer: Gmail software
  • Lower layers (platform/infra/physical): managed by Google, hidden from user

Using a GCP VM (IaaS):
  • Consumer manages OS/app on virtual infrastructure layer
  • Provider manages physical + virtualization foundations


------------------------------------------------------------------------
10.7 EXAM TIP
------------------------------------------------------------------------
Define reference model + draw layered stack + map to IaaS/PaaS/SaaS + mention
cross-cutting security/management + list consumer/provider roles.

11. DECISION GUIDES (WHICH MODEL TO CHOOSE?)
================================================================================

------------------------------------------------------------------------
11.1 CHOOSING SERVICE MODEL
------------------------------------------------------------------------
Choose IaaS when:
  • You need OS-level control / custom stack
  • Migrating legacy VMs (lift-and-shift)
  • Specialized software needs custom configuration

Choose PaaS when:
  • Primary goal is fast app development/deployment
  • You want provider-managed runtime/scaling
  • Team is developer-centric, not infra-centric

Choose SaaS when:
  • Need is a standard business application
  • Want minimal IT maintenance
  • Speed of adoption matters more than deep customization


------------------------------------------------------------------------
11.2 CHOOSING DEPLOYMENT MODEL
------------------------------------------------------------------------
Choose Public when:
  • Need agility and low upfront cost
  • Workloads are not legally restricted from public cloud

Choose Private when:
  • High sensitivity / strict control requirements
  • Organization can fund and staff private cloud

Choose Hybrid when:
  • Mix of sensitive and elastic public workloads
  • Cloud bursting or gradual migration needed

Choose Community when:
  • Several orgs share mission/compliance needs and costs


------------------------------------------------------------------------
11.3 REAL-LIFE DECISION EXAMPLE
------------------------------------------------------------------------
A fintech startup:
  • Public cloud + PaaS for customer mobile backend (speed)
  • Managed DB with strong encryption (DBaaS)
  • Keep certain compliance logs strategy aligned to regulations
  • Use SaaS tools (email/CRM) for operations

An exam answer that shows scenario → model choice scores well.

12. EXAM QUICK REFERENCE
================================================================================

------------------------------------------------------------------------
12.1 MUST-MEMORIZE DEFINITIONS
------------------------------------------------------------------------
• Service model — what capability is delivered & who manages what
• Deployment model — where cloud runs & who can access it
• IaaS — rent virtual infrastructure (VM/storage/network)
• PaaS — rent platform/runtime to deploy apps
• SaaS — rent ready software over Internet
• Hybrid cloud — composition of private + public (or multiple clouds bound together)
• Cloud architecture — component structure of cloud systems
• Reference model — conceptual layered framework of cloud roles/services


------------------------------------------------------------------------
12.2 MUST-MEMORIZE LISTS
------------------------------------------------------------------------
Service models (SPI): IaaS, PaaS, SaaS
Deployment models: Public, Private, Hybrid, Community
Other services (examples): DBaaS, FaaS, CaaS, IDaaS, Storage as a Service, DRaaS
Architecture components: Client, Application, Service, Runtime, Storage,
  Infrastructure, Management, Security, Internet
Reference roles: Consumer, Provider (, Broker, Auditor, Carrier)


------------------------------------------------------------------------
12.3 CONFUSING PAIRS
------------------------------------------------------------------------
Service model vs Deployment model:
  Service = WHAT you consume (IaaS/PaaS/SaaS)
  Deployment = WHERE/WHO (Public/Private/Hybrid/Community)

Private cloud vs Public cloud VPC:
  Private cloud = exclusive infrastructure for one org (often dedicated)
  VPC = logically isolated network inside a public cloud account

PaaS vs SaaS:
  PaaS = you build/deploy your app on managed platform
  SaaS = you use a finished app

IaaS vs Virtualization alone:
  Virtualization is a technology; IaaS is a service model delivering virtualized
  infrastructure as a metered cloud service.


------------------------------------------------------------------------
12.4 ONE-LINE MEMORY AIDS
------------------------------------------------------------------------
• SPI: Soft Pizza Illustration → Software, Platform, Infrastructure
• Control order: IaaS (most control) → PaaS → SaaS (least control)
• Types of cloud: PuPHiC → Public, Private, Hybrid, Community
