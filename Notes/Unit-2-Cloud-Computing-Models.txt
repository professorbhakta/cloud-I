2. CLOUD SERVICE MODELS (IaaS, PaaS, SaaS) — IN DEPTH
================================================================================

The three fundamental service models form the SPI stack:

  SPI = Software (SaaS) + Platform (PaaS) + Infrastructure (IaaS)

------------------------------------------------------------------------
2.1 INFRASTRUCTURE AS A SERVICE (IaaS)
------------------------------------------------------------------------

DEFINITION:
  Provides virtualized computing resources — VMs, storage, networks — over the
  Internet. Customer rents infrastructure instead of buying physical hardware.

MANAGED BY PROVIDER:  Hardware, Hypervisor, Physical Network
MANAGED BY CUSTOMER:  OS, Middleware, Applications, Data

USE CASES:
  • Hosting websites and web applications
  • Development and test environments
  • High-performance computing (HPC)
  • Disaster recovery and backup infrastructure
  • Companies needing full control over OS and software stack

EXAMPLES: AWS EC2, Google Compute Engine, Azure Virtual Machines

------------------------------------------------------------------------
2.2 PLATFORM AS A SERVICE (PaaS)
------------------------------------------------------------------------

DEFINITION:
  Provides a complete development and deployment platform. Provider manages
  servers, OS, runtime, and middleware; developer focuses on application code.

MANAGED BY PROVIDER:  Hardware, OS, Runtime, Middleware
MANAGED BY CUSTOMER:  Applications, Data

USE CASES:
  • Rapid application development
  • API development and deployment
  • Microservices development
  • Mobile backend services

EXAMPLES: Google App Engine, Heroku, Azure App Service, AWS Elastic Beanstalk

------------------------------------------------------------------------
2.3 SOFTWARE AS A SERVICE (SaaS)
------------------------------------------------------------------------

DEFINITION:
  Fully managed software delivered over the Internet. Users access via browser
  or app without installation or maintenance.

MANAGED BY PROVIDER:  Everything (Hardware through Application)
MANAGED BY CUSTOMER:  Data and user access configuration (limited)

USE CASES:
  • Email and collaboration (Gmail, Microsoft 365)
  • CRM (Salesforce)
  • ERP systems
  • Project management tools

EXAMPLES: Google Workspace, Salesforce, Microsoft 365, Zoom

------------------------------------------------------------------------
SPI COMPARISON TABLE (Exam Essential)
------------------------------------------------------------------------

Aspect           | IaaS              | PaaS                | SaaS
-----------------|-------------------|---------------------|-------------------
Control          | High              | Medium              | Low
Target User      | Sys admins,       | Developers          | End users
                 | network architects|                     |
What You Get     | VMs, storage,     | Dev platform +      | Ready-to-use
                 | networking        | deployment tools    | software
Management       | Manage OS & apps  | Manage apps only    | Just use software
Flexibility      | Most flexible     | Moderate            | Least flexible
Example          | AWS EC2           | Google App Engine   | Gmail

================================================================================

[Additional Context — Syllabus Topic: Other Cloud Services]

Beyond IaaS, PaaS, and SaaS, cloud providers offer specialized "as a Service"
models. Collectively known as XaaS (Anything as a Service).

SERVICE MODEL          | FULL FORM                    | DESCRIPTION
-----------------------|------------------------------|-----------------------------
FaaS                   | Function as a Service        | Run code in response to events;
                       |                              | serverless; pay per execution

  Umbrella term for the growing list of cloud service offerings delivered over

5. CLOUD ARCHITECTURE & COMPONENTS
================================================================================

DEFINITION:
  Cloud architecture is the overall design and structure of a cloud computing
  system. It explains how servers, storage, databases, applications, and
  networks are organized to deliver scalable, secure, reliable, and cost-effective
  services over the Internet.

THREE MAJOR ARCHITECTURAL COMPONENTS
-------------------------------------

1. FRONT END (Client Side)
   • User-facing side of the cloud system
   • Includes web browsers, mobile apps, client software
   • Provides GUI for uploading data, accessing apps, managing services
   Example: User logs into Gmail or Google Drive via browser on laptop/phone

2. BACK END (Cloud Provider Side)
   • Service provider's side where all resources are stored and managed
   • Includes:
       - Servers — process user requests
       - Storage systems — databases and storage devices
       - Virtualization — multiple VMs on single physical server
       - Management software — resource allocation, load balancing, monitoring
       - Security systems — encryption, authentication, access control
   • Handles requests, processes data, ensures availability
   Example: When user uploads a file, back end stores it securely for later access

3. NETWORK (Internet)
   • Connects front end and back end
   • Enables access from any location
   • Strong, reliable network essential for fast data transfer
   Example: Accessing cloud files from home, office, or remote location

ARCHITECTURE DIAGRAM (Text Representation):
  ┌──────────────┐         INTERNET          ┌──────────────────────────┐
  │  FRONT END   │ ◄──────────────────────► │  BACK END                │
  │  (Client)    │                           │  • Servers               │
  │  • Browser   │                           │  • Storage               │
  │  • Mobile App│                           │  • Virtualization        │
  │  • GUI       │                           │  • Management Software   │
  └──────────────┘                           │  • Security Systems      │
                                             └──────────────────────────┘

NINE DETAILED COMPONENTS OF CLOUD ARCHITECTURE
-----------------------------------------------

1. CLIENT INFRASTRUCTURE
   Front-end component providing GUI to interact with the cloud.

2. APPLICATION
   Any software or platform the client wants to access.

3. SERVICE
   Manages which type of service (SaaS/PaaS/IaaS) the client accesses
   based on requirements.

4. RUNTIME CLOUD
   Provides execution and runtime environment for virtual machines.

5. STORAGE
   Most important component — huge storage capacity to store and manage data.

6. INFRASTRUCTURE
   Host-level, application-level, and network-level services. Includes
   hardware and software: servers, storage, network devices, virtualization
   software, and other resources supporting the cloud model.

7. MANAGEMENT
   Manages application, service, runtime cloud, storage, infrastructure,
   and security. Establishes coordination between all back-end components.

8. SECURITY
   In-built back-end component implementing security mechanisms
   (encryption, authentication, access control).

9. INTERNET
   Medium through which front end and back end interact and communicate.

The NIST Cloud Computing Reference Architecture defines the major actors,
their activities, and how they interact in a cloud ecosystem.

FIVE ACTORS IN CLOUD REFERENCE MODEL
-------------------------------------

ACTOR              | ROLE
-------------------|--------------------------------------------------------
Cloud Consumer     | Person or organization that uses cloud services
Cloud Provider     | Organization that makes cloud services available
Cloud Auditor      | Independent party that conducts audits of cloud services
Cloud Broker       | Manages use, performance, and delivery of cloud services;
                   | negotiates relationships between providers and consumers
Cloud Carrier      | Provides connectivity and transport between consumers
                   | and providers (e.g., telecom/network companies)

CLOUD CONSUMER ACTIVITIES:
  • Requests services from cloud provider
  • Sets up service contracts (SLAs)
  • Uses and monitors cloud services
  • Pays for consumed resources

CLOUD PROVIDER ACTIVITIES:
  • Deploys and manages cloud infrastructure
  • Provisions services to consumers
  • Monitors and meters resource usage
  • Ensures security and availability

7. CONTAINERS, DOCKER & SERVERLESS COMPUTING
================================================================================

------------------------------------------------------------------------
7.1 CONTAINERS
------------------------------------------------------------------------

DEFINITION:
  A lightweight package containing an application along with everything it
  needs to run — libraries, system tools, configuration files. Runs the same
  way on any computer or cloud system without compatibility problems.

CONTAINER vs VIRTUAL MACHINE:
  • VM includes a full operating system → heavier, slower to start
  • Container shares the host OS kernel → faster, uses fewer resources
  • VM provides stronger isolation; containers are more portable and efficient

------------------------------------------------------------------------
7.2 DOCKER
------------------------------------------------------------------------

DEFINITION:
  Docker is a tool to create, run, and manage containers easily.
  If a container is the box holding an application, Docker builds, ships,
  and runs that box.

KEY POINT:
  Developers package an application with all dependencies and run it anywhere —
  laptop, server, or cloud — without worrying about system differences.

DOCKER WORKFLOW:
  1. Write Dockerfile (recipe for container)
  2. Build image from Dockerfile
  3. Run container from image
  4. Push image to registry (Docker Hub, GCR, ECR)
  5. Deploy container on any host with Docker installed

------------------------------------------------------------------------
7.3 SERVERLESS COMPUTING
------------------------------------------------------------------------

DEFINITION:
  Cloud model where you write and run code WITHOUT managing servers.
  Cloud provider fully handles setup, scaling, maintenance, and updates.
  You focus on code; pay only when code runs.

SERVERLESS vs PaaS (Exam Analogy):
  • PaaS → Renting a shop (always open, always running)
  • Serverless → Food delivery kitchen (cook only when order comes)

COMPARISON:
  Aspect          | PaaS                          | Serverless (FaaS)
  ----------------|-------------------------------|---------------------------
  Server mgmt     | Provider manages servers      | Provider manages everything
  Execution       | App runs continuously         | Functions run only when triggered
  Billing         | Pay while app is running      | Pay per execution/event
  Scaling         | Auto-scale app instances      | Auto-scale per function call
  Example         | Google App Engine (always on) | AWS Lambda (runs on upload event)

IMPORTANT EXAM POINT:
  A website on PaaS can move to serverless, but it requires REDESIGNING the
  backend into event-driven functions — not simply redeploying the same app.

EXAMPLES: AWS Lambda, Azure Functions, Google Cloud Functions

8. MULTI-TENANCY AND RESOURCE SHARING
================================================================================

MULTI-TENANCY
-------------
Architecture where a single cloud infrastructure or application serves multiple
users (tenants) simultaneously. Tenants share physical/virtual resources but
data, configurations, and operations are LOGICALLY ISOLATED.

Each tenant experiences the system as if it were dedicated solely to them.

RESOURCE SHARING
----------------
Pooling and dynamic allocation of CPU, memory, storage, and network bandwidth
among multiple tenants. Providers use virtualization, containers, and
automation to distribute resources efficiently based on demand.

Maximizes utilization, minimizes idle hardware — key cloud advantage.

IMPORTANCE OF MULTI-TENANCY
----------------------------
  • Foundation of scalability and cost efficiency in cloud
  • Multiple users share infrastructure → reduced hardware/operational costs
  • Enables elastic scaling, centralized management, faster updates
  • Without multi-tenancy: cloud would be expensive, less scalable, hard to maintain

THREE TYPES OF MULTI-TENANT ARCHITECTURE
-----------------------------------------

TYPE 1: SINGLE APPLICATION — SINGLE DATABASE
  • One shared app instance + one shared database for all tenants
  • Tenant data differentiated by Tenant ID in same tables
  • Logical isolation via authentication, authorization, access control
  • Pros: Highly cost-effective, easy maintenance (one update for all)
  • Cons: Limited isolation; DB issues affect all tenants
  • Used in: Large-scale SaaS (cost efficiency priority)

TYPE 2: SINGLE APPLICATION — MULTIPLE DATABASES
  • Shared app instance; each tenant gets separate database
  • Pros: Better data isolation, easier backup/recovery, regulatory compliance
  • Cons: More expensive (higher storage/management overhead)
  • Used in: Moderate customization, stronger data isolation needs

TYPE 3: MULTIPLE APPLICATION — MULTIPLE DATABASES
  • Each tenant gets dedicated app instance AND separate database
  • Pros: Highest isolation, security, customization; independent updates
  • Cons: Highest cost, reduced resource efficiency
  • Used in: Large enterprises, sensitive workloads, strict compliance

MULTI-TENANCY COMPARISON TABLE:
  Architecture              | Isolation | Cost    | Customization | Use Case
  --------------------------|-----------|---------|---------------|------------------
  Single App, Single DB     | Low       | Lowest  | Low           | Mass SaaS
  Single App, Multiple DBs  | Medium    | Medium  | Medium        | Regulated SaaS
  Multiple App, Multiple DBs| High      | Highest | High          | Enterprise

WORKING OF MULTI-TENANCY IN DIFFERENT ENVIRONMENTS
---------------------------------------------------

1. PUBLIC CLOUD
   Multiple organizations share provider's infrastructure. Isolation via VMs,
   identity management, encryption. High scalability, rapid provisioning.

2. PRIVATE CLOUD
   Multi-tenancy within one organization — departments/teams as tenants.
   Greater control, enhanced security, regulatory compliance.

3. CONTAINER ARCHITECTURE
   Tenants share OS kernel; isolated containers with resource limits and
   namespaces. High performance, efficient utilization; needs strong security
   against container escape attacks.

4. SERVERLESS COMPUTING
   Fully provider-managed multi-tenancy. Functions execute on shared
   infrastructure; resources auto-allocated on trigger, released after.
   Pay-per-use; limited control; performance may vary.

9. LOAD BALANCING IN CLOUD COMPUTING
================================================================================

DEFINITION:
  Process of distributing incoming network traffic or workload across multiple
  servers, VMs, or resources so no single system is overloaded.

TECHNICAL DEFINITION:
  Technique to optimize resource utilization, maximize throughput, minimize
  response time, and ensure high availability by evenly distributing
  workloads across computing resources.

WHY LOAD BALANCING IS REQUIRED
-------------------------------
  1. High Availability — Failed server? Traffic redirected to healthy servers
  2. Scalability — Supports horizontal scaling (add/remove servers dynamically)
  3. Performance Optimization — Prevents overload, reduces latency
  4. Efficient Resource Utilization — Optimal CPU, memory, bandwidth usage
  5. Reliability — Prevents Single Point of Failure (SPOF)

HOW LOAD BALANCING WORKS (5 Steps)
-----------------------------------
  1. Client sends request (browser, API call)
  2. Request reaches the load balancer
  3. Load balancer checks: server health, current load, configured algorithm
  4. Request forwarded to most suitable backend server
  5. Server processes request; response sent back via load balancer
  → Health checks run continuously to detect failed servers

LOAD BALANCING TECHNIQUES
--------------------------

TECHNIQUE              | DESCRIPTION                          | Cloud Suitability
-----------------------|--------------------------------------|-------------------
Static                 | Predefined rules; ignores current    | Poor — workloads
                       | system state                         | are dynamic
Dynamic                | Runtime decisions based on CPU,      | Excellent — monitors
                       | memory, bandwidth, response time     | and adapts
Centralized            | Single load balancer distributes     | Risk — bottleneck,
                       | all traffic                          | single point of failure
Distributed            | Multiple load balancers share        | Best for large data
                       | responsibility                       | centers; more complex

LOAD BALANCING ALGORITHMS (Exam Important)
-------------------------------------------

ALGORITHM              | HOW IT WORKS                         | BEST FOR
-----------------------|--------------------------------------|--------------------
Round Robin            | Sequential cyclic distribution       | Equal-capacity servers
Weighted Round Robin   | Cyclic but weighted by capacity      | Heterogeneous servers
Least Connections      | Server with fewest active connections| Long sessions, streaming
Least Response Time    | Fastest server + fewest connections | Performance-sensitive apps
Hash-Based             | Hash on client IP or URL             | Session persistence
                       | (same client → same server)          | (stateful apps)

TYPES OF LOAD BALANCERS
------------------------

1. SOFTWARE-BASED LOAD BALANCERS
   • Programs on VMs or standard servers
   • Operate at OSI Layer 4 (Transport) or Layer 7 (Application)
   • Features: content routing, SSL termination, health checks, caching
   • Pros: Flexible, cost-effective, cloud-native, easy to scale
   • Cons: Performance depends on underlying hardware; needs maintenance
   • Used in: Modern cloud, containers, microservices

2. HARDWARE-BASED LOAD BALANCERS
   • Dedicated physical appliances in data centers
   • Features: SSL offloading, DDoS protection, traffic inspection
   • Pros: High throughput, low latency, superior performance
   • Cons: Expensive, less flexible, hard to scale, high maintenance
   • Trend: Gradually replaced by software/cloud-native solutions

EXAMPLES:
  • AWS Elastic Load Balancer (ELB)
  • Google Cloud Load Balancing
  • Azure Load Balancer
  • NGINX, HAProxy (software-based)

10. SCALABILITY IN CLOUD COMPUTING
================================================================================

DEFINITION:
  Ability of a system to increase or decrease computing resources (CPU, RAM,
  storage, bandwidth, VMs, containers) according to workload without
  disrupting services.

TECHNICAL DEFINITION:
  Capability of cloud infrastructure to handle increasing or decreasing
  workloads by proportionally adjusting resource capacity while maintaining
  performance, availability, and system stability.

WHY SCALABILITY IS IMPORTANT
-----------------------------
  1. Dynamic Workloads — E-commerce spikes during sales; exams cause traffic surges
  2. Cost Efficiency — Pay-as-you-go; release resources when demand drops
  3. High Availability — Without scaling: overload, latency, downtime, crashes

HOW SCALABILITY WORKS IN CLOUD
-------------------------------
Uses combination of:
  • Virtualization
  • Resource pooling
  • Monitoring (CPU, memory, request rate)
  • Automation (Auto Scaling Groups)
  • Load balancing

Process:
  Demand increases → auto-scaling provisions more VMs/containers
  Demand decreases → unused resources de-provisioned
  Entire process is automatic, fast, transparent to end users

THREE TYPES OF SCALABILITY
---------------------------

1. VERTICAL SCALABILITY (Scale Up / Scale Down)
   Increase/decrease capacity of a SINGLE server (more CPU, RAM, storage).
   Example: Upgrade VM from 4 GB RAM to 16 GB RAM
   Advantages: Simple, no app changes, good for monolithic apps
   Limitations: Hardware limits, possible downtime, single point of failure

2. HORIZONTAL SCALABILITY (Scale Out / Scale In)
   Add/remove MULTIPLE servers, VMs, or containers.
   Example: Increase app instances from 5 to 20 during high traffic
   Advantages: High availability, fault tolerance, no single point of failure
   Limitations: Needs load balancing, complex architecture, stateless design

3. DIAGONAL SCALABILITY (Hybrid)
   Scale vertically first until limit reached, then scale horizontally.
   Provides flexibility, performance optimization, cost efficiency.
   Commonly used in modern cloud systems.

SCALABILITY vs ELASTICITY (Exam Distinction):
  • Scalability = Ability to handle growth (manual or automatic)
  • Elasticity = Automatic, rapid scaling based on real-time demand
  (Elasticity is a specialized form of scalability in cloud computing)

REAL-WORLD EXAMPLE — Video Streaming Platform:
  • Normal hours: Few servers handle requests
  • Peak hours/live events: Traffic increases
  • Auto-scaling launches additional servers
  • Load balancers distribute traffic across all servers
  • Traffic decreases: Extra servers terminated

11. SECURITY & COMPLIANCE IN CLOUD COMPUTING
================================================================================

Cloud introduces security and compliance challenges because data and
applications are hosted on third-party infrastructure.

------------------------------------------------------------------------
11.1 SECURITY IN CLOUD COMPUTING
------------------------------------------------------------------------

DEFINITION:
  Set of policies, technologies, controls, and best practices to protect
  cloud systems, data, and infrastructure from unauthorized access, breaches,
  cyberattacks, and service disruptions.

SHARED RESPONSIBILITY MODEL (Critical for Exams):
  ┌─────────────────────────────────────────────────────────────┐
  │  CUSTOMER RESPONSIBILITY          │  PROVIDER RESPONSIBILITY │
  │  • Data                            │  • Physical security     │
  │  • Applications                    │  • Hypervisor            │
  │  • Access management (IAM)         │  • Network infrastructure│
  │  • OS patches (in IaaS)            │  • Data center security  │
  │  • Encryption configuration        │  • Hardware maintenance  │
  └─────────────────────────────────────────────────────────────┘
  Note: Responsibility shifts based on service model (IaaS vs PaaS vs SaaS)

KEY SECURITY CHALLENGES
------------------------
  1. Data Breaches and Data Leakage — Weak access controls, misconfiguration
  2. Data Loss — Accidental deletion, hardware failure, ransomware
  3. Insecure APIs and Interfaces — Poorly secured APIs exploited by attackers
  4. Account Hijacking — Stolen credentials lead to data theft
  5. Insider Threats — Employees with excessive privileges

CLOUD SECURITY MECHANISMS AND CONTROLS
---------------------------------------

1. IDENTITY AND ACCESS MANAGEMENT (IAM)
   Controls who accesses resources and what actions they perform.
   Includes: authentication, authorization, RBAC, MFA.

2. DATA ENCRYPTION
   a. Data at Rest — Encrypted when stored
   b. Data in Transit — Encrypted during transmission (TLS/SSL)
   c. Data in Use — Protected during processing

3. NETWORK SECURITY
   Firewalls, VPNs, IDS (Intrusion Detection), IPS (Intrusion Prevention)

4. MONITORING AND LOGGING
   Continuous monitoring, logging, auditing for suspicious activities

5. BACKUP AND DISASTER RECOVERY
   Regular backups and DR plans for business continuity

------------------------------------------------------------------------
11.2 COMPLIANCE IN CLOUD COMPUTING
------------------------------------------------------------------------

DEFINITION:
  Adhering to legal, regulatory, industry, and organizational standards for
  data protection, privacy, security, and governance.

WHY COMPLIANCE IS IMPORTANT:
  • Protects sensitive and personal data
  • Ensures legal and regulatory adherence
  • Avoids legal penalties and fines
  • Builds customer trust and confidence
  • Ensures transparency and accountability

COMMON COMPLIANCE REQUIREMENTS:
  1. Data Privacy Regulations — GDPR (EU), DPDP Act (India), CCPA (California)
  2. Industry Standards — HIPAA (healthcare), PCI-DSS (payments), SOC 2
  3. Audit and Reporting — Maintain logs, documentation, compliance reports

SECURITY vs COMPLIANCE (Exam Essential):
  • Security = Protecting systems and data from THREATS (technical)
  • Compliance = Meeting LEGAL and REGULATORY requirements (procedural)
  • Both are closely related but distinct concepts

12. PRICING MODELS & COST MANAGEMENT
================================================================================

Major cloud advantage: flexible, cost-effective pricing. Improper usage can
cause unexpected costs — making cost management essential.

FIVE PRICING MODELS
--------------------

1. PAY-AS-YOU-GO (On-Demand)
   Charged only for resources actually consumed (compute time, storage, transfer).
   Billing per second/minute/hour. No upfront investment.
   Pros: No capital expenditure, high flexibility, ideal for unpredictable workloads
   Cons: Costs rise rapidly if unmonitored; not economical for steady long-term use

2. SUBSCRIPTION-BASED
   Fixed monthly or yearly fee for predefined services regardless of usage (within limits).
   Common for SaaS and enterprise solutions.
   Pros: Predictable cost, easy budgeting, stable workloads
   Cons: Paying for unused resources; less flexible than PAYG

3. RESERVED INSTANCES
   Commit to resources for 1 or 3 years for significant discounts.
   Suitable for steady, predictable workloads.
   Pros: Lower cost, cost predictability
   Cons: Less flexibility, long-term commitment required

4. SPOT / PREEMPTIBLE INSTANCES
   Unused computing capacity at very low cost; can be terminated anytime.
   Suitable for batch processing, analytics, non-critical workloads.
   Pros: Extremely low cost, efficient use of spare capacity
   Cons: No availability guarantee; not for critical applications

5. FREEMIUM
   Limited resources free; upgrade to paid plans for more.
   Pros: Good for learning and experimentation; no financial risk
   Cons: Limited resources; not for production workloads

COST MANAGEMENT TECHNIQUES
-----------------------------
  1. Resource Monitoring — Track CPU, memory, storage, network traffic
  2. Auto-Scaling — Prevent over-provisioning; pay only for needed resources
  3. Right-Sizing — Choose appropriate instance type (not too big or small)
  4. Budgeting & Cost Alerts — Set spending limits; alerts on threshold breach
  5. Reserved + Spot Instances — Combine for stable and non-critical workloads
  6. Storage Optimization — Delete unused data; use appropriate storage tiers;
     implement data lifecycle policies

BENEFITS OF EFFECTIVE COST MANAGEMENT:
  • Reduced operational cost
  • Better budget planning
  • Efficient resource utilization
  • Avoidance of unexpected expenses
  • Improved ROI

CHALLENGES IN CLOUD COST MANAGEMENT:
  1. Complex pricing structures
  2. Hidden data transfer costs
  3. Over-provisioning of resources
  4. Lack of visibility in multi-cloud environments
  5. Difficulty predicting future usage

16. CONFUSING PAIRS — CLEAR DIFFERENCES (High-Scoring in Exams)
================================================================================

------------------------------------------------------------------------
PaaS vs SERVERLESS (Very Common Exam Trap)
------------------------------------------------------------------------
  PaaS            = App environment ALWAYS running (like a shop always open)
  Serverless      = Code runs ONLY when triggered (kitchen cooks on order)

  Billing:
    PaaS        → Pay while platform/app is running
    Serverless  → Pay per function execution/event

  Migration:
    Cannot simply move PaaS app to serverless — must REDESIGN into
    event-driven functions.

  Examples:
    PaaS        → Google App Engine (always on)
    Serverless  → AWS Lambda (runs on file upload trigger)

------------------------------------------------------------------------
CONTAINER vs VIRTUAL MACHINE
------------------------------------------------------------------------
  VM              = Full OS per instance; stronger isolation; heavier
  Container       = Shares host OS kernel; lighter; faster startup

  Exam line: "Containers package the app; VMs package the app + full OS."

  Docker creates CONTAINERS, not VMs.

------------------------------------------------------------------------
VERTICAL vs HORIZONTAL SCALING
------------------------------------------------------------------------
  VERTICAL (Scale Up/Down)   = Bigger single server (more RAM/CPU)
  HORIZONTAL (Scale Out/In)  = More servers added/removed

  Vertical  → Simple but has hardware limits + single point of failure
  Horizontal → Needs load balancer + stateless design; better for cloud

  DIAGONAL = Scale up first until limit, then scale out.

------------------------------------------------------------------------
STATIC vs DYNAMIC LOAD BALANCING
------------------------------------------------------------------------
  STATIC    = Predefined rules; ignores current CPU/memory load
  DYNAMIC   = Real-time monitoring; redirects to less-loaded servers

  Exam trap: Static LB is NOT suitable for cloud (workloads are dynamic).

------------------------------------------------------------------------
CENTRALIZED vs DISTRIBUTED LOAD BALANCING
------------------------------------------------------------------------
  CENTRALIZED   = One load balancer — risk of bottleneck + SPOF
  DISTRIBUTED   = Multiple LBs share work — better for large data centers

------------------------------------------------------------------------
SOFTWARE vs HARDWARE LOAD BALANCER
------------------------------------------------------------------------
  SOFTWARE  = Flexible, cheaper, cloud-native (NGINX, AWS ELB)
  HARDWARE  = Dedicated appliance, expensive, high throughput, less flexible

  Trend: Cloud moving toward software-based load balancers.

------------------------------------------------------------------------
SECURITY vs COMPLIANCE
------------------------------------------------------------------------
  SECURITY    = Protecting systems from THREATS (technical controls)
  COMPLIANCE  = Meeting LEGAL/REGULATORY rules (GDPR, HIPAA, PCI-DSS)

  Exam line: "Security is what you DO; compliance is what you MUST PROVE."

  Related but different — both needed in cloud.

------------------------------------------------------------------------
PAY-AS-YOU-GO vs SUBSCRIPTION vs RESERVED vs SPOT
------------------------------------------------------------------------
  PAYG        = Flexible, no commitment; cost can spike if unmonitored
  SUBSCRIPTION= Fixed monthly fee; predictable; may waste unused resources
  RESERVED    = 1-3 year commitment; big discount; less flexible
  SPOT        = Cheapest; can be terminated anytime; batch jobs only
  FREEMIUM    = Free tier for learning; not for production

------------------------------------------------------------------------
ROUND ROBIN vs WEIGHTED ROUND ROBIN vs LEAST CONNECTIONS
------------------------------------------------------------------------
  Round Robin           = Equal servers, cyclic order; ignores load
  Weighted Round Robin  = Stronger servers get more requests
  Least Connections     = Sends to server with fewest active sessions
  Least Response Time   = Fastest + fewest connections (best performance)
  Hash-based            = Same client → same server (session persistence)

------------------------------------------------------------------------
SERVICE MODEL vs DEPLOYMENT MODEL (Repeat Trap from Unit 1)
------------------------------------------------------------------------
  SERVICE     = WHAT you get (IaaS, PaaS, SaaS)
  DEPLOYMENT  = WHERE/HOW hosted (Public, Private, Hybrid, Community)

  Unit 2 focuses on HOW cloud systems are structured and operated —
  architecture, tenancy, scaling, security, pricing.

17. DECISION GUIDES — "WHICH ONE TO CHOOSE?"
================================================================================

WHEN TO USE WHICH MULTI-TENANT ARCHITECTURE?
  Mass-market SaaS (thousands of small customers)     → 1 App, 1 DB
  Regulated industry needing data separation        → 1 App, Multiple DBs
  Large enterprise / strict compliance / custom app → Multiple App, Multiple DBs

WHEN TO USE WHICH SCALING TYPE?
  Legacy monolithic app, quick fix                    → Vertical
  Web app with unpredictable traffic, high availability → Horizontal
  Modern cloud-native system                        → Diagonal (best practice)

WHEN TO USE WHICH PRICING MODEL?
  Startup testing ideas, unpredictable traffic      → Pay-as-you-go / Freemium
  Stable SaaS with fixed users                      → Subscription
  Production app running 24×7 for 1-3 years         → Reserved Instances
  Batch analytics, non-critical background jobs     → Spot / Preemptible
  Learning cloud / college labs                     → Freemium

WHEN TO USE WHICH LOAD BALANCING ALGORITHM?
  All servers equal capacity                          → Round Robin
  Servers with different specs (big + small VMs)      → Weighted Round Robin
  Long-lived sessions (streaming, chat, DB connections)→ Least Connections
  Performance-critical (low latency apps)           → Least Response Time
  User must stay on same server (shopping cart)      → Hash-based

CONTAINER vs VM — WHEN TO USE?
  Need full OS isolation, run Windows on Linux host   → VM
  Microservices, fast deployment, DevOps pipelines  → Container (Docker)
  Maximum portability with minimal overhead           → Container

------------------------------------------------------------------------
Q: Explain cloud architecture with its components. (5-8 marks)
------------------------------------------------------------------------
ANSWER STRUCTURE:
  1. Definition: Cloud architecture = overall design of how cloud resources
     are organized to deliver scalable, secure, reliable services.

  2. Three major parts:
     • Front End — client side (browser, mobile app, GUI)
     • Back End — provider side (servers, storage, virtualization, security)
     • Network — Internet connecting front and back end

  3. Nine components (list all): Client Infrastructure, Application, Service,
     Runtime Cloud, Storage, Infrastructure, Management, Security, Internet

  4. Example: User uploads file via browser (front end) → travels over
     Internet (network) → stored on provider servers (back end).

  5. Closing: Good architecture enables scalability, security, and cost
     efficiency.

------------------------------------------------------------------------
Q: What is multi-tenancy? Explain its types. (8 marks)
------------------------------------------------------------------------
ANSWER STRUCTURE:
  1. Definition: Single cloud infrastructure serves multiple tenants;
     resources shared physically, data isolated logically.

  2. Importance: Cost efficiency, scalability, centralized updates.

  3. Three types (use table):

  | Type                  | Isolation | Cost   | Use Case          |
  |-----------------------|-----------|--------|-------------------|
  | 1 App, 1 DB           | Low       | Lowest | Mass SaaS         |
  | 1 App, Multiple DBs   | Medium    | Medium | Regulated SaaS    |
  | Multiple App, Multi DB| High      | Highest| Enterprise        |

  4. Mention Tenant ID for logical separation in single DB model.

  5. Works in: Public cloud, private cloud (dept as tenants), containers,
     serverless.

------------------------------------------------------------------------
Q: Explain load balancing in cloud computing. (5-8 marks)
------------------------------------------------------------------------
ANSWER STRUCTURE:
  1. Definition: Distributing incoming traffic across multiple servers
     to prevent overload and ensure high availability.

  2. Why needed: High availability, scalability, performance, no SPOF.

  3. Working (5 steps): Client request → Load balancer → health check →
     algorithm selects server → response returned.

  4. Techniques: Static (poor for cloud), Dynamic (best), Centralized,
     Distributed.

  5. Algorithms: Round Robin, Weighted RR, Least Connections, Hash-based.

  6. Types: Software-based (NGINX, AWS ELB) vs Hardware-based appliances.

------------------------------------------------------------------------
Q: Explain scalability in cloud. (5 marks)
------------------------------------------------------------------------
ANSWER STRUCTURE:
  1. Definition: Ability to adjust resources (CPU, RAM, VMs) per workload.

  2. Why important: Dynamic traffic, cost efficiency, high availability.

  3. Three types:
     • Vertical — scale up/down single server
     • Horizontal — add/remove multiple servers (needs load balancer)
     • Diagonal — vertical first, then horizontal

  4. How it works: Monitoring → Auto Scaling Groups → provision/deprovision
     resources automatically.

  5. Example: E-commerce site scales up during Diwali sale, scales down after.

------------------------------------------------------------------------
Q: Security and compliance in cloud computing. (8-10 marks)
------------------------------------------------------------------------
ANSWER STRUCTURE:
  1. Shared Responsibility Model (draw or describe provider vs customer).

  2. Security challenges (any 4): Data breaches, data loss, insecure APIs,
     account hijacking, insider threats.

  3. Security controls (any 4): IAM, encryption (at rest/in transit),
     network security (firewall, VPN), monitoring/logging, backup/DR.

  4. Compliance: Legal adherence — GDPR, HIPAA, PCI-DSS, audit logs.

  5. Key distinction: Security = technical protection; Compliance = legal
     and regulatory requirements.

------------------------------------------------------------------------
Q: Explain pricing models and cost management in cloud. (8 marks)
------------------------------------------------------------------------
ANSWER STRUCTURE:
  1. Five pricing models: PAYG, Subscription, Reserved, Spot, Freemium
     (one line each with advantage).

  2. Cost management techniques: Monitoring, auto-scaling, right-sizing,
     budget alerts, reserved+spot mix, storage optimization.

  3. Benefits: Lower cost, better ROI, no surprise bills.

  4. Challenges: Complex pricing, hidden transfer costs, over-provisioning.

19. COMMON MISTAKES STUDENTS MAKE (Avoid These)
================================================================================

MISTAKE 1: Saying serverless means no servers exist
  ✗ WRONG: "Serverless = no servers."
  ✓ RIGHT: Servers exist but are fully managed by provider; you don't manage them.

MISTAKE 2: Confusing Runtime Cloud with PaaS
  Runtime Cloud = component that provides execution environment for VMs
  PaaS = entire service model. Related but not the same thing.

MISTAKE 3: Listing only Round Robin for load balancing algorithms
  Exam expects: Weighted RR, Least Connections, Least Response Time, Hash-based.

MISTAKE 4: Saying vertical scaling has no downtime
  ✓ RIGHT: Vertical scaling MAY require downtime during RAM/CPU upgrade.

MISTAKE 5: Using spot instances for critical production apps
  ✓ RIGHT: Spot = batch/non-critical only; can be terminated anytime.

MISTAKE 6: Forgetting security is SHARED responsibility
  Provider secures infrastructure; customer secures their data, apps, IAM.

MISTAKE 7: Mixing up multi-tenancy types
  "Single app single DB" = LOWEST isolation, not highest.
  "Multiple app multiple DB" = HIGHEST isolation.

MISTAKE 8: Saying static load balancing is good for cloud
  ✓ RIGHT: Dynamic load balancing is preferred — cloud workloads change constantly.

MISTAKE 9: Docker = virtualization hypervisor
  ✓ RIGHT: Docker = containerization tool. Different from hypervisor-based VMs.

MISTAKE 10: Only mentioning encryption "at rest" for security
  Include all three: at rest, in transit, and in use (when asked comprehensively).

20. VIVA / ORAL QUESTIONS (Quick Fire Answers)

Q: What are the 3 major parts of cloud architecture?
A: Front end, back end, and network (Internet).

Q: Name 4 back-end elements.
A: Servers, storage, virtualization, management software, security systems
   (any 4).

Q: What is Docker in one line?
A: Tool to create, ship, and run containers.

Q: PaaS vs Serverless — one line each?
A: PaaS = always-on platform; Serverless = event-triggered functions, pay per run.

Q: What is SPOF?
A: Single Point of Failure — one component failure brings whole system down.
   Load balancing helps prevent this.

Q: What is right-sizing?
A: Choosing the correct instance size — not too big (waste money) or too
   small (poor performance).

Q: What is IAM?
A: Identity and Access Management — controls who can access what in cloud.

Q: Layer 4 vs Layer 7 load balancer?
A: L4 = transport (IP/port); L7 = application (HTTP URL, content-based).

Q: Why is multi-tenancy important?
A: Enables cost sharing, scalability, and efficient resource utilization.

Q: Can you move a PaaS website to serverless directly?
A: No — requires redesigning backend into event-driven functions.

Q: What is auto-scaling?
A: Automatically adding/removing resources based on demand metrics (CPU, traffic).

Q: Reserved vs Spot instances?
A: Reserved = committed long-term, discounted. Spot = cheap spare capacity,
   can be killed anytime.

22. REAL-WORLD MINI CASE STUDIES (Makes Answers Stand Out)
================================================================================

CASE 1: E-COMMERCE DIWALI SALE → Load Balancing + Horizontal Scaling
  Flipkart/Amazon during sale: traffic spikes 10×. Auto-scaling adds servers;
  load balancer distributes requests. After sale, extra servers removed.
  Lesson: Horizontal scaling + dynamic load balancing = handle peak traffic.

CASE 2: STARTUP COST CONTROL → PAYG + Right-Sizing
  Startup uses AWS t2.micro (free tier), monitors CPU. When app grows,
  right-sizes to t3.small instead of jumping to oversized instance.
  Lesson: PAYG + monitoring + right-sizing prevents bill shock.

CASE 3: NETFLIX → Multi-Tenancy at Massive Scale
  Millions of users share AWS infrastructure. Each account's data logically
  isolated. Single application architecture with massive shared infrastructure.
  Lesson: 1 App + shared resources model at global scale.

CASE 4: BANK → Security + Compliance + Hybrid
  Bank uses encryption (security) + PCI-DSS compliance for card data.
  Core systems private; customer portal on public cloud.
  Lesson: Security controls + compliance standards + hybrid deployment together.

CASE 5: DATA ANALYTICS BATCH JOB → Spot Instances
  Company runs nightly report on 1 million records using spot instances.
  If instance terminated, job restarts. Saves 70% vs on-demand pricing.
  Lesson: Spot pricing for fault-tolerant, non-critical workloads.

CASE 6: MICROSERVICES STARTUP → Containers + Docker
  Team packages each microservice in Docker container. Deploys consistently
  from laptop to GCP. Faster than managing individual VMs.
  Lesson: Containers for portable, scalable microservice architecture.
