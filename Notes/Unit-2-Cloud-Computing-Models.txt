0. UNIT 2 BIG PICTURE: WHAT CLOUD COMPUTING MODELS ACTUALLY MEAN
================================================================================

Cloud computing models are the organized ways in which cloud computing is
delivered, deployed, shared, managed, priced and secured. In Unit 1, cloud
computing is usually introduced as a way to provide computing resources over a
network on demand. Unit 2 asks a deeper question: when an organization says it is
using "cloud", exactly what kind of cloud is it using, who owns it, who manages
which part of it, how is it architected, and what responsibilities remain with
the user?

The word "model" is important because cloud computing is not one single product.
It is a collection of models. A student using Google Drive, a developer deploying
an application on Heroku, and a company renting virtual machines from AWS EC2 are
all using cloud computing, but they are not using it at the same level. The
student is using SaaS because the complete application is ready. The developer on
Heroku is using PaaS because the platform hides server management. The company
on EC2 is using IaaS because it directly controls virtual machines, storage and
networking. Unit 2 teaches how to identify these differences correctly.

Cloud models can be classified from two major angles. The first angle is the
service model, which answers, "What is being delivered as a service?" The usual
service models are IaaS, PaaS and SaaS, and many modern services extend them into
DBaaS, FaaS, CaaS, AIaaS, SECaaS and similar forms. The second angle is the
deployment model, which answers, "Where does the cloud run and who can use it?"
The usual deployment models are public, private, hybrid and community cloud.
Together, these two angles allow us to describe most real cloud systems clearly.

For example, an online banking application may use a private cloud for sensitive
transaction processing, a public cloud for customer notification services, and a
SaaS tool for internal email. Its deployment model may therefore be hybrid, while
its service models may include IaaS, PaaS and SaaS at the same time. This is why
exam answers should not treat cloud models as isolated definitions. A strong
answer connects the model to control, cost, security, scalability, responsibility
and practical use.

Unit 2 also introduces cloud architecture and the cloud computing reference
model. Cloud architecture explains the technical arrangement of front end,
network, back end services, virtualization, storage, monitoring, security and
management systems. The reference model explains the roles involved in a cloud
ecosystem, especially the NIST actors: Cloud Consumer, Cloud Provider, Cloud
Auditor, Cloud Broker and Cloud Carrier. These roles help us understand that
cloud is not only a technology arrangement but also a service relationship among
different parties.

The practical importance of this unit is high. Before building any cloud system,
a company must choose whether it needs IaaS or PaaS, public or private cloud,
containers or serverless, reserved instances or pay-as-you-go, self-managed
security or provider-managed security. Wrong choices can increase cost, reduce
performance or create compliance risk. Correct choices make systems scalable,
available, secure and easier to operate. Therefore Unit 2 forms the decision-
making foundation for the later units on virtualization, storage, security and
cloud platforms.

1. BASIC TERMINOLOGIES AND FOUNDATIONS
================================================================================

Cloud service model means the level at which a cloud provider offers computing
capability to the user. If the provider offers raw infrastructure such as virtual
machines, disks and networks, the model is IaaS. If the provider offers a ready
platform for deploying code, the model is PaaS. If the provider offers a complete
application used through a browser or client app, the model is SaaS. The service
model is therefore mainly about the boundary between provider responsibility and
customer responsibility.

Cloud deployment model means the ownership, access and placement style of the
cloud environment. Public cloud is owned by a provider and offered to many
customers over the internet. Private cloud is dedicated to one organization.
Hybrid cloud combines private and public environments. Community cloud is shared
by organizations with common needs. The deployment model is therefore mainly
about who uses the cloud, who owns or controls it, and how isolated it must be.

SPI stack means the Software, Platform and Infrastructure stack. Infrastructure
is the base because all computing needs hardware, networking and storage.
Platform sits above infrastructure because software developers need runtime
environments, databases, middleware and deployment tools. Software sits at the
top because end users usually want complete applications rather than servers or
runtime environments. The SPI stack is a useful memory structure for IaaS, PaaS
and SaaS.

Virtualization is the technique by which one physical server is divided into
multiple logical machines. A hypervisor controls the hardware and allows many
virtual machines to run independently. Virtualization is central to IaaS because
cloud providers use it to rent computing capacity in flexible units. Without
virtualization, a provider would have to dedicate entire physical machines to
customers, which would reduce efficiency and increase cost.

Multi-tenancy means that several customers, called tenants, share the same
underlying cloud infrastructure or application while keeping their data and
configuration logically separated. Multi-tenancy is one of the main reasons cloud
providers can reduce cost. It is also one of the main reasons cloud security must
be carefully designed, because sharing should never allow one tenant to access
another tenant's data.

Elasticity means the ability of a system to automatically increase or decrease
resources according to demand. Scalability is the broader ability to handle
growth by adding resources or improving architecture. Elasticity is often
automatic and demand-driven, while scalability may be planned, manual or
architectural. A website that automatically adds servers during an exam result
announcement and removes them later is using elasticity.

Cloud orchestration means coordinating many cloud resources so they work together
as one system. When an application is deployed, orchestration may create servers,
attach storage, configure load balancers, set firewall rules, start containers,
register monitoring and apply scaling policies. In modern cloud computing, manual
configuration of every component is avoided because automation reduces errors and
improves repeatability.

Service Level Agreement, commonly called SLA, is a formal agreement that defines
the expected quality of a cloud service. It may specify uptime, performance,
support response time, backup frequency and compensation if the provider fails to
meet commitments. For example, an SLA of 99.9 percent availability means the
service is expected to be unavailable only for a limited amount of time in a
given period. SLA is important because cloud customers depend on services they do
not fully own.

Shared responsibility means the provider and customer divide responsibility for
security, operations and management. In IaaS, the provider secures the physical
data center and basic infrastructure, while the customer secures the operating
system, applications and data. In PaaS, the provider manages more of the runtime
and platform. In SaaS, the provider manages almost everything except user access,
data usage and configuration choices. This concept appears repeatedly in cloud
security and compliance questions.

2. TYPES OF CLOUD AND WAYS OF CLASSIFYING CLOUD
================================================================================

The phrase "types of cloud" is sometimes used broadly and sometimes narrowly.
Broadly, it can refer to both service models and deployment models. Narrowly, in
many syllabi, types of cloud refers mainly to public, private, hybrid and
community cloud. To avoid confusion in exams, write the opening sentence clearly.
For example, "Cloud may be classified by service delivery into IaaS, PaaS and
SaaS, and by deployment into public, private, hybrid and community cloud." This
single sentence prevents the answer from mixing categories incorrectly.

Public cloud is a cloud environment owned and operated by a third-party provider
such as Amazon Web Services, Microsoft Azure, Google Cloud, IBM Cloud or Oracle
Cloud. It is made available to multiple customers over the internet. The provider
owns the infrastructure and customers rent services when needed. Public cloud is
popular because it offers fast provisioning, global reach, high scalability and a
pay-as-you-go pricing style. Its major limitation is that customers have less
physical control over infrastructure, so they must understand security,
compliance and data location requirements carefully.

Private cloud is a cloud environment dedicated to a single organization. It may
run inside the organization's own data center or be hosted by a third party, but
it is not shared with unrelated customers in the same way a public cloud is.
Private cloud is preferred when an organization needs strong control, strict
compliance, custom security policies or predictable internal workloads. Banks,
government departments and large enterprises often use private cloud for
sensitive systems. However, private cloud can be costly because the organization
must pay for dedicated capacity, skilled staff, maintenance and upgrades.

Hybrid cloud combines private cloud and public cloud so that workloads and data
can move or coordinate between them. The key idea is not simply using two clouds
separately; the key idea is integration. A retail company may keep customer
payment data in a private cloud but use a public cloud for product images, search
and seasonal scaling. Hybrid cloud is useful when some workloads require control
and others require flexibility. Its challenge is complexity: networking,
identity, monitoring, data synchronization and governance must work across
different environments.

Community cloud is a cloud environment shared by several organizations that have
common requirements. These requirements may involve legal compliance, security,
mission, industry standards or data sharing. For example, several universities
may share a research cloud, or several hospitals may share a health-sector cloud
with common privacy requirements. Community cloud can reduce cost compared with a
fully private cloud while still offering more specialized governance than a
general public cloud. The difficulty is coordinating policies and funding among
the member organizations.

Multi-cloud means using services from more than one public cloud provider. A
company may use AWS for compute, Google Cloud for analytics and Microsoft Azure
for identity or enterprise integration. Multi-cloud is not the same as hybrid
cloud. Hybrid cloud emphasizes combining private and public environments.
Multi-cloud emphasizes using multiple providers. Multi-cloud can reduce provider
lock-in and improve resilience, but it increases operational complexity because
teams must manage different consoles, billing models, identity systems and
networking patterns.

Virtual private cloud, often shortened to VPC, is a logically isolated network
inside a public cloud. It gives customers private IP ranges, subnets, route
tables, gateways and security controls while still using provider-owned
infrastructure. VPC is important because it gives public cloud users a private
networking boundary. It does not make the cloud a private cloud in the deployment
model sense, because the underlying environment is still a public cloud shared by
many customers.

Edge cloud is a newer cloud pattern in which computing resources are placed
closer to users or devices. Instead of sending all data to a central data center,
some processing happens near mobile towers, factories, hospitals, vehicles or
Internet of Things devices. Edge cloud is useful for low-latency use cases such
as autonomous systems, video analytics, gaming and industrial control. It does
not replace central cloud; it extends cloud architecture toward the edge of the
network.

Cloud may also be classified by purpose. Storage clouds focus on object storage,
file storage and backup. Compute clouds focus on virtual machines, containers and
serverless functions. Data clouds focus on databases, warehouses and analytics.
Application clouds focus on business software such as CRM, email or ERP. These
purpose-based labels are not always formal syllabus categories, but they help
students connect cloud models to real products.

3. SERVICE MODELS: IAAS, PAAS, SAAS AND THE SPI STACK
================================================================================

The three classical cloud service models are Infrastructure as a Service,
Platform as a Service and Software as a Service. These are often called the SPI
models because they form the Software-Platform-Infrastructure stack. The easiest
way to understand them is to ask what the user receives. In IaaS, the user
receives infrastructure building blocks. In PaaS, the user receives an
application platform. In SaaS, the user receives a finished application.

IaaS gives the highest control among the three major models. Customers can choose
virtual machines, operating systems, storage volumes, networks, firewall rules
and sometimes specialized hardware such as GPUs. Because customers control more,
they must manage more. They install patches, configure operating systems,
deploy applications, secure instances and monitor capacity. IaaS is suitable
when applications need custom environments, legacy software support, special
networking or deep administrative control.

PaaS gives developers a ready environment to build, test and deploy applications
without managing the underlying servers. The customer usually uploads code,
selects runtime settings and connects managed services such as databases,
queues, caches or identity services. The provider handles servers, operating
system patching, runtime maintenance, scaling features and deployment pipelines.
PaaS is suitable for teams that want to focus on application logic rather than
server administration.

SaaS gives users a complete application delivered over the internet. The user
usually logs in through a browser or mobile app and configures settings according
to business needs. The provider manages everything behind the application,
including infrastructure, platform, updates, backups and most security controls.
SaaS is suitable when the organization wants a ready solution such as email,
office collaboration, customer relationship management, accounting, learning
management or project tracking.

The movement from IaaS to SaaS is a movement from control toward convenience. In
IaaS, the customer can customize deeply but must manage many technical details.
In PaaS, the customer sacrifices some control but gains faster development. In
SaaS, the customer sacrifices most technical control but gains immediate business
use. This trade-off is one of the most important ideas in Unit 2.

The service model also affects cost. IaaS may look cheap at first because a
virtual machine can be rented by the hour, but hidden costs appear in
administration, patching, monitoring, security and scaling. PaaS may cost more
per unit of compute but reduce staff effort. SaaS usually charges per user or per
subscription and may be cheaper for standard business needs because the provider
spreads development and operations cost across many customers.

The service model affects security responsibility. In IaaS, customers must secure
the operating system and application. In PaaS, customers secure code, data and
configuration. In SaaS, customers mainly secure accounts, permissions and data
usage. A common exam mistake is writing that "the cloud provider handles all
security." This is false. Cloud security is shared, and the share changes across
models.

The service model also affects vendor lock-in. IaaS may be easier to migrate if
the application is built on common operating systems and portable tools, though
networking and storage details still create lock-in. PaaS can create stronger
lock-in because code may depend on provider-specific APIs, runtimes or services.
SaaS can create business data and process lock-in because users may depend on the
application's workflows, reports and integrations.

4. INFRASTRUCTURE AS A SERVICE IN DEPTH
================================================================================

Infrastructure as a Service is a cloud model in which the provider offers
virtualized computing infrastructure over a network. The customer rents resources
such as virtual machines, block storage, object storage, virtual networks,
firewalls, load balancers and sometimes dedicated hosts. The provider is
responsible for physical buildings, power, cooling, networking equipment,
servers, storage hardware and the virtualization layer. The customer is
responsible for the operating system, applications, data, identity configuration
and many security settings.

The main idea of IaaS is to convert infrastructure from a capital purchase into
an on-demand service. In a traditional data center, a company buys servers,
installs them, connects them to a network and maintains them for years. In IaaS,
the company requests a virtual server in minutes and pays only for the capacity
used. This is valuable when demand changes quickly or when a team must experiment
without waiting for procurement.

Compute is the most visible part of IaaS. A virtual machine behaves like a
physical computer from the user's perspective. The user can choose CPU, memory,
operating system image, region, disk size and network settings. Cloud providers
offer different instance families for general purpose workloads, memory-heavy
applications, compute-heavy tasks, storage-intensive systems and GPU-based
machine learning. This variety allows customers to match infrastructure to the
workload.

Storage in IaaS appears in several forms. Block storage works like a disk
attached to a virtual machine and is useful for databases or operating system
volumes. Object storage stores data as objects inside buckets and is useful for
images, videos, backups and logs. File storage provides shared file systems that
many machines can mount. Archive storage stores rarely accessed data at lower
cost. A strong answer should mention that cloud storage is not one single thing;
different storage types solve different problems.

Networking in IaaS includes virtual networks, subnets, IP addresses, gateways,
route tables, firewalls, VPNs, direct connections and load balancers. These
networking services allow customers to design secure and reliable application
environments. For example, a web server may be placed in a public subnet while a
database is placed in a private subnet. Security groups or firewall rules can
allow only the web server to connect to the database.

IaaS is commonly used for website hosting, test and development environments,
disaster recovery, high-performance computing, big data processing, temporary
campaign workloads and migration of existing applications. It is especially
useful when an organization has software that cannot easily be rewritten for PaaS
or SaaS. A legacy payroll system, for example, may be moved from a physical
server to a cloud virtual machine with fewer code changes.

The benefits of IaaS include flexibility, fast provisioning, reduced upfront
investment, scalability, disaster recovery options and global availability. An
organization can start with one server and later scale to many servers across
regions. It can also create backups and snapshots more easily than in many
traditional environments. IaaS supports experimentation because resources can be
created and deleted as needed.

The limitations of IaaS include management overhead, configuration complexity,
security responsibility and cost surprises. If a team leaves unused virtual
machines running, costs increase. If operating systems are not patched, security
risk increases. If networks are misconfigured, data may be exposed. Therefore
IaaS gives freedom, but it also requires discipline.

Examples of IaaS include Amazon EC2, Azure Virtual Machines, Google Compute
Engine, Oracle Cloud Compute, IBM Cloud Virtual Servers and DigitalOcean
Droplets. Related IaaS services include AWS EBS for block storage, Azure Managed
Disks, Google Persistent Disk, AWS VPC, Azure Virtual Network and Google VPC.
When writing examples, use well-known services but do not make the answer only a
list of brand names; explain what they provide.

5. PLATFORM AS A SERVICE IN DEPTH
================================================================================

Platform as a Service is a cloud model in which the provider offers a ready
environment for developing, testing, deploying and running applications. The
customer writes application code and configures the application, while the
provider manages servers, operating systems, runtime environments, middleware and
many operational tasks. PaaS is popular because it reduces the time between
writing code and making it available to users.

The central promise of PaaS is developer productivity. A developer can push code
to a platform, and the platform can build it, run it, expose it through a URL,
scale it and connect it to managed services. Instead of spending time installing
web servers, patching operating systems or configuring deployment scripts, the
developer focuses on application logic. This is why PaaS is often used by
startups, academic projects and teams that want rapid delivery.

PaaS usually includes runtime support. A runtime is the environment required to
execute an application, such as Java, Node.js, Python, PHP, Ruby, .NET or Go. The
platform may also provide build tools, environment variables, logging, scaling
settings, health checks and deployment slots. Some PaaS offerings support
container-based deployments, while others deploy code directly.

PaaS also commonly includes managed backing services. A backing service is a
service used by an application, such as a database, cache, message queue, object
storage, email service or authentication service. In a PaaS environment, the
developer can attach these services without manually installing and maintaining
them. This makes the application easier to build and operate, but it may also
increase dependency on provider-specific features.

The benefits of PaaS include faster development, lower operations burden,
automatic scaling features, integrated monitoring, simplified deployment and
better consistency across development and production. Because the provider
controls the platform, it can apply security patches and runtime updates more
efficiently. PaaS can also support collaboration because teams deploy through a
shared pipeline rather than manually changing servers.

The limitations of PaaS include reduced control, runtime restrictions, platform
lock-in and possible difficulty with unusual workloads. If an application needs a
special operating system module, custom kernel setting or unusual networking
configuration, PaaS may not allow it. If the application uses proprietary PaaS
APIs deeply, migration to another provider may require code changes. Therefore
PaaS is best when speed and simplicity matter more than low-level control.

Examples of PaaS include Google App Engine, Heroku, Azure App Service, AWS
Elastic Beanstalk, Red Hat OpenShift and Cloud Foundry. Kubernetes platforms can
also behave like PaaS when they provide developers with a deployment platform
that hides cluster management. However, Kubernetes by itself is often closer to a
container orchestration platform than a complete PaaS unless additional developer
services are added.

A student can remember PaaS by thinking of it as "bring your code, not your
server." In IaaS, the user thinks about virtual machines. In PaaS, the user
thinks about applications, runtimes and deployment. This difference is often the
key to identifying PaaS examples in objective questions.

6. SOFTWARE AS A SERVICE IN DEPTH
================================================================================

Software as a Service is a cloud model in which the provider delivers a complete
application to users over a network. Users do not install and maintain the full
software stack on their own systems. They access the service through a browser,
mobile app or thin client. The provider manages infrastructure, platform,
application code, updates, backups, availability and most technical security.

SaaS is the most user-facing cloud model. Many people use SaaS without thinking
of it as cloud computing. Gmail, Google Workspace, Microsoft 365, Salesforce,
Zoom, Dropbox, Slack, Canva, GitHub and many learning management systems are
examples of SaaS. The user focuses on work, communication, documents, meetings,
sales records or learning activities rather than servers and software
installation.

The major benefit of SaaS is immediate usability. A department can start using a
SaaS product by creating accounts and configuring settings. Updates arrive
automatically, and users normally receive new features without installing
software manually. SaaS also supports remote access because the application is
available through the internet. This became especially important for online
classes, remote work and distributed teams.

SaaS usually follows a subscription or per-user pricing model. Instead of buying
a perpetual license and installing software on local machines, the organization
pays monthly or annually. This can reduce upfront cost, but long-term cost must
be monitored because unused accounts, premium plans and add-ons can become
expensive. SaaS cost management therefore includes reviewing active users and
license levels.

SaaS has limitations. Users have less control over application behavior, upgrade
timing, backend architecture and data storage location. Customization is limited
to what the provider supports. Integration with local systems may require APIs or
connectors. If the provider experiences an outage, customers cannot directly fix
the backend. If the provider changes pricing or features, customers may have to
adapt.

Security in SaaS is often misunderstood. The provider secures the application
infrastructure, but the customer must manage user access, strong passwords,
multi-factor authentication, permissions, data sharing policies and user
training. Many SaaS breaches happen not because the provider's data center fails,
but because accounts are compromised or files are shared too widely. Therefore
SaaS users still have important security responsibilities.

SaaS is suitable when the business process is standard and a ready solution is
available. Email, file sharing, video meetings, project management, customer
support, CRM and HR systems are common SaaS use cases. SaaS is less suitable
when an organization needs a highly customized application, special regulatory
control or unique business logic that no SaaS product can support.

7. COMPARISON OF IAAS, PAAS AND SAAS
================================================================================

The comparison of IaaS, PaaS and SaaS is one of the most common Unit 2 exam
questions. A strong comparison should not only list examples. It should compare
the delivered capability, user type, control level, provider responsibility,
customer responsibility, advantages and limitations. The following table gives a
compact comparison, followed by explanatory paragraphs.

| Point of comparison | IaaS | PaaS | SaaS |
|---|---|---|---|
| What is delivered | Virtualized infrastructure | Application development platform | Complete application |
| Main user | System admin, DevOps engineer, architect | Developer, application team | End user, business team |
| Customer controls | OS, apps, data, network config | Code, data, app config | Data, user settings, access |
| Provider controls | Physical infra and virtualization | Infra, OS, runtime, platform | Almost full stack |
| Flexibility | Highest | Medium | Lowest technical flexibility |
| Convenience | Lower | Higher | Highest |
| Example | AWS EC2, Azure VM | Heroku, App Engine | Gmail, Salesforce |
| Best for | Custom systems, migration, control | Fast app development | Ready business functions |

IaaS gives the customer the most technical control because the customer receives
basic infrastructure and builds upward. This is useful when the workload needs
custom operating system settings, special software, legacy compatibility or
detailed network design. The cost of this control is operational work. Someone
must patch the OS, configure security, install monitoring and manage backups.

PaaS reduces infrastructure work by giving developers a ready platform. It is a
middle path. The customer still writes and controls the application, but the
provider manages the underlying runtime and servers. It is especially useful for
web applications, APIs and mobile backends where the main goal is fast
development and frequent deployment.

SaaS removes most technical work from the customer. The customer simply uses the
application and manages accounts, configuration and data. This is the best model
when the requirement is common and a mature product already exists. However, SaaS
is not ideal when deep customization or backend control is required.

In exam answers, the control-versus-convenience trade-off should be emphasized.
As we move from IaaS to PaaS to SaaS, customer control decreases and provider
management increases. As provider management increases, the user experience
becomes simpler, but customization becomes more limited. This single idea can
explain many differences in cost, responsibility, security and migration.

8. OTHER CLOUD SERVICES BEYOND THE MAIN SPI MODELS
================================================================================

Modern cloud computing includes many service categories beyond IaaS, PaaS and
SaaS. These services are often named using the pattern "something as a Service."
They do not replace the SPI models; they extend them. In exams, "other cloud
services" can be explained as specialized cloud offerings that provide databases,
storage, security, networks, desktops, analytics, artificial intelligence,
containers or functions as managed services.

Database as a Service, or DBaaS, provides managed databases without requiring the
customer to install database software on a server. The provider handles many
tasks such as provisioning, patching, backups, replication and monitoring.
Examples include Amazon RDS, Azure SQL Database, Google Cloud SQL, MongoDB Atlas
and Firebase Realtime Database. DBaaS is useful because databases are critical
and difficult to operate correctly, but customers still must design schemas,
queries, access policies and backup retention according to business needs.

Storage as a Service, or STaaS, provides storage capacity over the network.
Object storage such as Amazon S3, Azure Blob Storage and Google Cloud Storage is
widely used for media files, backups, logs, static websites and data lakes.
Storage services often provide durability, lifecycle policies, access control and
replication. The important idea is that users do not buy disks directly; they
consume storage as a scalable service.

Function as a Service, or FaaS, is a serverless model in which small pieces of
code run in response to events. Examples include AWS Lambda, Azure Functions and
Google Cloud Functions. The user writes functions, and the provider runs them
when triggered by events such as HTTP requests, file uploads, queue messages or
scheduled timers. FaaS is powerful for event-driven workloads, but it may have
limits such as execution time, cold starts and provider-specific APIs.

Container as a Service, or CaaS, provides a managed environment for running
containers. Examples include Google Kubernetes Engine, Azure Kubernetes Service,
Amazon Elastic Kubernetes Service and Amazon ECS. CaaS is useful when teams want
the portability of containers but do not want to manage all cluster operations.
It often sits between IaaS and PaaS: more flexible than simple PaaS, but easier
than managing containers directly on virtual machines.

Desktop as a Service, or DaaS, provides virtual desktops to users over a network.
Employees can access a managed desktop environment from different devices. This
is useful for remote work, training labs, call centers and secure access to
corporate applications. The provider or IT department manages the desktop images,
updates and access policies.

Network as a Service, or NaaS, provides networking capabilities such as virtual
private networks, load balancing, DNS, content delivery, firewalls and direct
connections as services. NaaS matters because cloud systems depend heavily on
software-defined networking. In traditional data centers, network changes may
require physical device configuration. In cloud, many network functions are
created through APIs and dashboards.

Security as a Service, or SECaaS, provides security functions through cloud-based
services. These may include identity management, web application firewalls,
DDoS protection, vulnerability scanning, security monitoring, email security and
endpoint protection. SECaaS allows organizations to access specialized security
capabilities without building every tool themselves.

Artificial Intelligence as a Service, or AIaaS, provides machine learning and AI
capabilities through APIs or managed platforms. Examples include speech-to-text,
translation, image recognition, recommendation systems, model training platforms
and generative AI services. AIaaS is important because it allows developers to
use advanced models without building all infrastructure and algorithms from
scratch.

Backup as a Service, Disaster Recovery as a Service and Monitoring as a Service
are also common. Backup services protect data, disaster recovery services help
restore systems after failures, and monitoring services collect metrics, logs and
alerts. These services show that cloud computing is not only about running
applications; it is also about operating them reliably.


================================================================================
9. DEPLOYMENT MODELS: PUBLIC, PRIVATE, HYBRID AND COMMUNITY CLOUD
================================================================================

Deployment models describe how cloud infrastructure is owned, accessed and
shared. They are different from service models. A public cloud can offer IaaS,
PaaS and SaaS. A private cloud can also offer IaaS, PaaS and internal SaaS. This
is why exam answers should clearly separate the question "what service is being
provided?" from the question "where and for whom is it deployed?"

Public cloud is the most visible deployment model. It is owned by a provider and
offered to many customers. Its strengths are scalability, global coverage, rapid
provisioning, broad service catalog and usage-based pricing. Public cloud is
excellent for startups, web applications, analytics experiments, seasonal
workloads and global services. Its weaknesses are lower physical control,
dependency on provider availability, possible data residency concerns and the
need for strong governance to prevent cost and security mistakes.

Private cloud is dedicated to one organization. It may be built using tools such
as VMware, OpenStack, Nutanix, Azure Stack or private Kubernetes platforms. Its
strengths are control, customization, predictable governance and possible
alignment with strict compliance requirements. Its weaknesses are cost, capacity
planning burden and the need for skilled internal teams. Private cloud should
not be confused with traditional virtualization. A true private cloud should
provide self-service, automation, resource pooling, measured service and elastic
provisioning as far as possible.

Hybrid cloud combines environments in a coordinated way. A good hybrid design
usually includes shared identity, secure connectivity, monitoring, policy
management and data movement. Hybrid cloud is useful when organizations cannot
move everything to public cloud at once or when sensitive and non-sensitive
workloads need different environments. The complexity of hybrid cloud is higher
because failure, latency and security must be managed across boundaries.

Community cloud is shared by organizations with common requirements. It can be
managed by one of the organizations, by a third party or by a combination. The
important point is common purpose. For example, a group of universities may share
a research computing cloud where data policies and research tools are aligned.
A group of healthcare organizations may share a cloud that follows healthcare
privacy rules. Community cloud balances shared cost with specialized governance.

The choice of deployment model depends on security requirements, budget,
regulatory constraints, workload variability, existing infrastructure, staff
skills and business strategy. A small e-commerce company may choose public cloud
because it needs speed and seasonal scaling. A defense department may choose
private cloud because control and confidentiality dominate. A hospital network
may choose hybrid cloud because patient records need strict control while public
facing appointment systems need scalability.

10. CLOUD ARCHITECTURE: LAYERS, COMPONENTS AND WORKING VIEW
================================================================================

Cloud architecture is the design of the components that make cloud computing
work. It includes the front end used by customers, the network that connects
customers to services, the back end where compute and storage run, and the
management systems that provide provisioning, monitoring, billing, security and
automation. A simple definition is: cloud architecture is the structured
arrangement of cloud components and their relationships.

The front end is the part visible to users or administrators. It may be a web
browser, mobile application, command-line interface, software development kit or
management console. Through the front end, users request services, upload code,
configure applications, view dashboards or consume SaaS applications. The front
end should be easy to use, but it must also be secure because it often controls
powerful cloud resources.

The network connects users to cloud services and connects cloud components to
one another. It includes the internet, private links, virtual networks, routers,
gateways, DNS, content delivery networks and load balancers. Cloud networking is
software-defined, meaning many network functions are created and managed through
software rather than only physical cabling. A well-designed network improves
performance, isolation and security.

The back end includes servers, storage systems, databases, virtualization
platforms, containers, application runtimes and management services. Users may
not see the physical hardware, but it is still present in data centers. The cloud
provider abstracts this hardware into services. The back end must handle
resource allocation, failure recovery, redundancy, data durability, scaling and
service monitoring.

Virtualization and containerization are important architectural technologies.
Virtualization allows multiple virtual machines to run on one physical machine.
Containerization packages an application with its dependencies so it can run
consistently across environments. Both improve resource utilization and
portability, but they operate differently. Virtual machines virtualize hardware,
while containers virtualize the operating system environment.

Cloud management software controls provisioning, scheduling, monitoring, billing,
metering and policy enforcement. When a user creates a virtual machine, the
management layer selects a physical host, allocates storage, configures network
settings and updates billing records. This automation is what makes self-service
cloud possible. Without management software, cloud would become manual hosting.

Security architecture includes identity and access management, encryption,
network segmentation, firewalls, key management, logging, threat detection and
backup. Security is not a separate decoration added at the end; it must be part
of every layer. For example, the front end needs authentication, the network
needs segmentation, storage needs encryption, and management APIs need auditing.

Cloud architecture is usually designed for availability. Availability means the
system remains usable even when some components fail. Cloud providers use
multiple data centers, availability zones, replication, health checks and load
balancers to reduce downtime. Application architects must also design for
failure by avoiding single points of failure, backing up data and using multiple
instances for critical services.

In an exam diagram, a basic cloud architecture can show users at the left, the
internet or network in the middle, and cloud services at the right. Inside the
cloud, show compute, storage, database, virtualization, security, monitoring and
management. Add load balancing before application servers and show databases in
a protected area. This simple diagram can support many written answers.

11. CLOUD COMPUTING REFERENCE MODEL AND NIST ACTORS
================================================================================

The cloud computing reference model describes the major roles and interactions
in a cloud ecosystem. The NIST model is widely used because it provides a clear
vocabulary for cloud relationships. The five major NIST actors are Cloud
Consumer, Cloud Provider, Cloud Auditor, Cloud Broker and Cloud Carrier. Each
actor has a distinct role, and understanding these roles helps explain how cloud
services are delivered and governed.

The Cloud Consumer is the person or organization that uses cloud services. A
consumer may be an individual using a SaaS application, a developer using PaaS or
an enterprise renting IaaS. The consumer selects services, agrees to service
terms, configures resources, uses applications and pays for consumption. The
consumer also has responsibilities such as protecting credentials, configuring
access controls and managing data.

The Cloud Provider is the organization that offers cloud services. The provider
operates infrastructure, platforms or applications depending on the service
model. It may provide physical data centers, virtualization, storage, networking,
application hosting, monitoring, support and billing. Examples include AWS,
Microsoft Azure, Google Cloud, Salesforce and many SaaS vendors. The provider's
responsibilities depend on the model, but it always plays the central service
delivery role.

The Cloud Auditor is an independent party that assesses cloud services,
security, performance and compliance. Auditors may review whether controls meet
standards such as ISO 27001, SOC 2, PCI DSS or government regulations. They may
also examine logs, policies, disaster recovery procedures and access controls.
The auditor increases trust because cloud consumers often cannot directly inspect
every provider facility and system.

The Cloud Broker is an intermediary that helps consumers use cloud services. A
broker may help compare providers, integrate services, manage multiple clouds,
negotiate contracts or add value through monitoring and governance. In simple
terms, a broker stands between consumers and providers to make cloud selection,
integration or management easier. Cloud brokerage becomes important in hybrid
and multi-cloud environments.

The Cloud Carrier provides connectivity and transport between cloud consumers and
cloud providers. Internet service providers, telecom networks and dedicated
connectivity services can act as carriers. The carrier may not own the cloud
application, but it is essential because cloud services are delivered over
networks. Poor connectivity can make a good cloud service unusable, so the
carrier role matters for performance and availability.

The NIST actors interact in practical ways. A university as a cloud consumer may
use Microsoft 365 from a cloud provider. A telecom company acts as the cloud
carrier by providing internet connectivity. A security firm may act as auditor
by checking compliance. A managed service provider may act as broker by helping
the university integrate identity, backup and monitoring across services. This
example shows that cloud computing is an ecosystem, not only a technical stack.

In exam answers, define the reference model first, then explain each actor in
separate paragraphs, then draw or describe the relationships. Avoid writing only
one-word meanings. A good answer explains why each actor exists and gives one
practical example.

12. CONTAINERS, DOCKER AND SERVERLESS COMPUTING
================================================================================

Containers are lightweight packages that include an application and the
dependencies needed to run it, such as libraries, runtime files and configuration
metadata. A container does not include a full guest operating system like a
virtual machine. Instead, it shares the host operating system kernel while
keeping processes isolated. This makes containers fast to start, efficient in
resource use and portable across environments that support the same container
runtime.

The main problem containers solve is environment inconsistency. A developer may
say, "It works on my machine," while the application fails on a test server
because the server has different libraries or configuration. Containers reduce
this problem by packaging the application environment in a standard image. The
same image can run on a laptop, test server, private cloud or public cloud
container service.

A virtual machine virtualizes hardware, while a container virtualizes the
operating system environment. A virtual machine includes a guest operating system
and runs on a hypervisor. A container shares the host kernel and runs on a
container runtime. Because VMs include a full operating system, they provide
strong isolation and can run different OS types on the same host, but they are
heavier. Containers are lighter and faster, but they depend on the host kernel
and require careful isolation configuration.

| Comparison point | Virtual machine | Container |
|---|---|---|
| Abstraction level | Hardware virtualization | OS-level virtualization |
| Operating system | Each VM has its own guest OS | Containers share host kernel |
| Startup time | Usually slower | Usually faster |
| Resource usage | Heavier | Lighter |
| Isolation | Stronger by default | Strong, but kernel-shared |
| Portability | Portable as VM image | Highly portable as container image |
| Typical use | Legacy apps, full OS control | Microservices, DevOps, cloud-native apps |

Docker is a popular platform for building, shipping and running containers.
Docker introduced a developer-friendly workflow using Dockerfiles, images,
registries and containers. A Dockerfile describes how to build an image. An image
is a read-only template containing application code and dependencies. A registry
stores images, such as Docker Hub, GitHub Container Registry, Amazon ECR or
Google Artifact Registry. A running container is an instance of an image.

The Docker workflow usually begins with writing application code and a
Dockerfile. The Dockerfile may start from a base image such as Python, Node,
Nginx or Ubuntu. It then copies files, installs dependencies, sets environment
variables and defines the command to run the application. The developer builds
the image, tests it locally, pushes it to a registry, and then deploys it to a
server, Kubernetes cluster or cloud container service. This workflow makes
application delivery more repeatable.

Docker Compose is often used in development to run multiple containers together.
A web application may require an application container, database container and
cache container. Compose describes these services in a YAML file so the whole
local environment can start with one command. In production, larger systems often
use Kubernetes or managed container services to schedule and manage containers
across many machines.

Kubernetes is a container orchestration platform. It manages deployment,
scaling, service discovery, rolling updates, self-healing and configuration for
containers. Kubernetes can run on public cloud, private cloud or local clusters.
Managed Kubernetes services such as GKE, AKS and EKS reduce the burden of
operating the control plane. Kubernetes is not exactly IaaS, PaaS or SaaS by
itself; depending on how it is offered, it can be part of CaaS or a platform
layer for cloud-native applications.

Serverless computing is a cloud execution model in which the cloud provider
automatically manages servers, scaling and much of the runtime infrastructure.
The term does not mean there are no servers. It means users do not provision or
manage servers directly. Serverless includes Function as a Service, where code
runs as functions, and serverless managed services such as serverless databases,
queues, APIs and workflows.

In Function as a Service, the developer writes small functions that respond to
events. An event may be an HTTP request, a file upload, a database change, a
message in a queue or a scheduled time. The provider runs the function only when
needed and charges mainly for execution time and number of requests. This model
is attractive for irregular workloads because idle functions usually cost little
or nothing.

Serverless has benefits such as reduced server management, automatic scaling,
fine-grained billing and faster development for event-driven applications. It is
useful for image processing after upload, sending notifications, API backends,
scheduled cleanup jobs, IoT event handling and lightweight automation. It allows
developers to focus on business logic rather than server capacity.

Serverless also has limitations. Cold starts may occur when a function has not
run recently and the provider must initialize a runtime. Execution time limits
make serverless unsuitable for some long-running workloads. Debugging and local
testing can be harder because the cloud event environment must be simulated.
Vendor lock-in can be strong because event formats, permissions and service
integrations differ across providers.

PaaS and serverless are related but not identical. PaaS usually runs a complete
application on a managed platform. The application may stay running continuously,
and the developer thinks in terms of apps, runtimes and deployments. Serverless
usually runs small functions or managed components triggered by events, and the
developer thinks in terms of events, functions and service integrations.

| Comparison point | PaaS | Serverless/FaaS |
|---|---|---|
| Unit of deployment | Application or service | Function or event handler |
| Server management | Hidden mostly | Hidden almost completely |
| Scaling | Often configured at app level | Automatic per event/request |
| Billing | App instances, resources or plan | Requests and execution duration |
| Best for | Web apps and APIs | Event-driven tasks and irregular workloads |
| Limitation | Platform constraints | Cold starts, time limits, lock-in |

Containers and serverless are both important in modern cloud careers. Containers
provide packaging and portability. Serverless provides event-driven execution
without server management. Many real systems use both: containers for core
microservices and serverless functions for background tasks. A good cloud
architect chooses based on workload pattern, team skill, cost, latency and
operational needs.

13. MULTI-TENANCY AND RESOURCE SHARING
================================================================================

Multi-tenancy is a core cloud principle in which multiple customers or tenants
share the same underlying resources while remaining logically separated. A tenant
may be a company, department, user group or customer account. Resource sharing
allows providers to use infrastructure efficiently, reduce cost and offer
services at scale. The challenge is to ensure that sharing does not violate
privacy, performance or security.

The first common architecture is shared application and shared database. In this
approach, all tenants use the same application instance and the same database,
with tenant identifiers used to separate records. This model is cost-efficient
and easy for the provider to update because one application version serves many
customers. It is common in SaaS products with many small tenants. The downside is
that isolation must be designed very carefully. A bug in tenant filtering can
expose data across tenants, and a noisy tenant may affect performance if limits
are not enforced.

The second architecture is shared application with separate databases or
schemas. Here, tenants may use the same application code, but each tenant has a
separate database, schema or storage area. This improves data isolation and can
make backup, migration and compliance easier for individual tenants. It costs
more than the fully shared model because each tenant needs more separate
resources. It is suitable for enterprise SaaS where customers require stronger
isolation or individual data management.

The third architecture is separate application instances on shared
infrastructure. In this approach, each tenant gets a separate application
instance, container, namespace or virtual machine, while the provider still uses
shared physical infrastructure. This gives stronger isolation and customization
but reduces efficiency. It is suitable for high-value customers, regulated
workloads or applications that require tenant-specific versions. The provider
must manage many instances, so automation becomes essential.

| Multi-tenant architecture | Main benefit | Main limitation | Typical use |
|---|---|---|---|
| Shared app, shared database | Lowest cost, easiest updates | Weakest isolation if poorly designed | Mass-market SaaS |
| Shared app, separate DB/schema | Better data isolation | More operational overhead | Enterprise SaaS |
| Separate app instances on shared infra | Strong isolation and customization | Highest cost and complexity | Regulated or premium tenants |

In public cloud, multi-tenancy exists at many levels. Physical servers may host
virtual machines from different customers. Storage systems may store objects from
many accounts. SaaS applications may serve thousands of organizations through
shared application code. Public cloud providers use virtualization, identity
controls, encryption, network isolation and monitoring to keep tenants separate.

In private cloud, the tenants may be departments or business units within the
same organization. For example, a university private cloud may serve the
computer science department, examination department and library. The privacy risk
may be lower than in public cloud because all tenants belong to the same
organization, but governance is still needed. Departments should not accidentally
consume all shared resources or access each other's data.

In container platforms, multi-tenancy can be implemented using namespaces,
resource quotas, network policies and role-based access control. Kubernetes
clusters often host applications from many teams. Without quotas, one team can
consume too much CPU or memory. Without network policies, one application may
reach another application unnecessarily. Container multi-tenancy is powerful but
requires careful platform engineering.

In serverless computing, multi-tenancy is mostly hidden by the provider. Many
customers' functions run on shared provider infrastructure, but customers see
only their functions and configuration. The provider must isolate execution
environments, manage permissions and prevent cross-tenant leakage. Customers
must still configure IAM permissions carefully because a function with excessive
permissions can damage data within the customer's own account.

Resource sharing improves utilization through pooling. Instead of dedicating a
separate physical server to each customer, a provider pools many servers and
allocates capacity dynamically. If one customer is idle while another is busy,
the provider can use capacity more effectively. This is one reason cloud can be
cheaper and more scalable than isolated traditional infrastructure.

The risks of multi-tenancy include data leakage, side-channel attacks, noisy
neighbor performance problems, misconfigured access control and compliance
concerns. Cloud providers reduce these risks through isolation technologies,
encryption, monitoring, patching and contractual controls. Customers reduce
their side of the risk through correct identity management, least privilege,
network segmentation and data classification.

For exam writing, explain multi-tenancy as both an economic and technical idea.
It lowers cost through sharing, but it requires logical isolation. Then describe
the three architecture types with pros and cons. This gives a richer answer than
simply writing "many users share the same cloud."

14. LOAD BALANCING IN CLOUD COMPUTING
================================================================================

Load balancing is the process of distributing incoming traffic or work across
multiple servers, containers, functions or services so that no single resource is
overloaded. In cloud computing, load balancing is essential because applications
must handle variable demand, failures and global users. A single server may fail
or become slow, but a group of servers behind a load balancer can provide better
availability and performance.

Load balancing is needed for five major reasons. First, it improves performance
by spreading requests across multiple resources. Second, it improves availability
because traffic can be sent away from failed instances. Third, it supports
scalability because new servers can be added behind the load balancer. Fourth,
it improves maintenance because servers can be removed temporarily without
stopping the whole application. Fifth, it supports efficient resource use because
traffic distribution can match server capacity.

The working of a load balancer can be explained in five steps. In the first step,
a user sends a request to the application address, such as a domain name. In the
second step, DNS or networking directs the request to the load balancer rather
than directly to an application server. In the third step, the load balancer
checks available backend targets and may consider health checks, capacity or
algorithm rules. In the fourth step, it forwards the request to a selected
server, container or service. In the fifth step, it monitors the response and
continues routing future traffic, removing unhealthy targets if needed.

Load balancing can happen at different layers. Layer 4 load balancing works at
the transport layer using information such as IP address and port. It is fast and
useful for TCP or UDP traffic. Layer 7 load balancing works at the application
layer using information such as HTTP path, hostname, headers or cookies. It is
more intelligent and can route `/api` requests to one service and `/images`
requests to another. DNS load balancing distributes users using DNS responses,
often across regions. Global load balancing routes users to the nearest or
healthiest region.

Round Robin is a simple load balancing algorithm in which requests are sent to
servers one by one in order. If there are three servers A, B and C, requests may
go to A, then B, then C, then A again. It is easy to understand and works well
when servers have similar capacity and requests require similar processing. Its
weakness is that it does not consider whether one server is already busy or
whether some requests are heavier than others.

Weighted Round Robin improves Round Robin by giving more traffic to stronger
servers. If server A has twice the capacity of server B, A can be given a higher
weight. This is useful when backend servers have different CPU, memory or
performance levels. It still may not reflect real-time load perfectly, but it is
better than simple Round Robin in mixed-capacity environments.

Least Connections sends new requests to the server with the fewest active
connections. This is useful when request processing time varies. A server with
many active connections is probably busy, so the load balancer sends new work to
a less busy server. Least Connections is common for web applications where some
requests are quick and others take longer.

Least Response Time considers server response speed and sometimes active
connections. It sends traffic to the server that is responding fastest. This can
improve user experience because the algorithm adapts to real performance. It
requires the load balancer to measure response times accurately, and sudden
changes in workload may still require careful tuning.

Hash-based load balancing uses a hash of some request attribute, such as client
IP address, session ID, URL or header, to choose a backend server. It is useful
when session persistence is needed, meaning the same user's requests should go
to the same server. However, if servers are added or removed, basic hashing may
redistribute many users unless consistent hashing or similar techniques are used.

Software load balancers run as software on general-purpose servers or as managed
cloud services. Examples include Nginx, HAProxy, Envoy, Traefik and cloud load
balancers. They are flexible, programmable and suitable for cloud-native
environments. Hardware load balancers are specialized appliances traditionally
used in data centers. They can provide high performance, but they are less
flexible and can be expensive. In cloud computing, managed software-defined load
balancers are very common because they integrate with autoscaling and monitoring.

Cloud examples include AWS Elastic Load Balancing, which offers Application Load
Balancer, Network Load Balancer and Gateway Load Balancer. Azure offers Azure
Load Balancer and Application Gateway. Google Cloud offers Cloud Load Balancing,
including global HTTP(S) load balancing. Kubernetes uses Services and Ingress
controllers to route traffic to pods. These examples show that load balancing is
not a separate optional add-on; it is a standard part of cloud architecture.

Load balancing also connects with health checks. A health check is a test used
to decide whether a backend target is ready to receive traffic. The load
balancer may request a health endpoint such as `/health` and expect a successful
response. If the target fails repeatedly, the load balancer stops sending
traffic to it. Health checks are essential because sending users to failed
servers defeats the purpose of load balancing.

In an exam answer, define load balancing, explain why it is needed, describe the
five-step working, then compare algorithms. If marks are higher, add software
versus hardware load balancers and cloud examples. A diagram showing users,
load balancer and multiple servers can make the answer stronger.

15. SCALABILITY, ELASTICITY AND CAPACITY PLANNING
================================================================================

Scalability is the ability of a system to handle increased workload by adding
resources or improving architecture. A scalable application can support more
users, more data or more requests without unacceptable performance loss. Cloud
computing is strongly associated with scalability because resources can be
provisioned quickly, and many cloud services are designed to grow with demand.

Vertical scalability, also called scaling up, means increasing the capacity of a
single machine or instance. For example, a small virtual machine with 2 CPUs and
4 GB RAM may be replaced by a larger one with 8 CPUs and 32 GB RAM. Vertical
scaling is simple because the application may not need major architectural
changes. Its limitation is that every machine has a maximum size, and scaling up
may require restart or downtime. It can also become expensive at higher sizes.

Horizontal scalability, also called scaling out, means adding more machines,
containers or service instances. Instead of making one server larger, the system
uses many servers together. Horizontal scaling is common for web applications,
microservices and distributed systems. It works well with load balancing because
requests can be spread across instances. Its challenge is that the application
must be designed to run across multiple instances, especially regarding sessions,
databases and shared state.

Diagonal scalability combines vertical and horizontal scaling. A system may first
scale vertically to a reasonable instance size and then scale horizontally by
adding more instances. This approach is practical because very small instances
may not be efficient, while very large single instances may be costly or risky.
Diagonal scaling gives flexibility by using both strategies according to demand.

Elasticity is the ability to automatically add or remove resources according to
current workload. Scalability is about the ability to grow; elasticity is about
dynamic adjustment. A system can be scalable without being elastic if an admin
manually adds servers. A system is elastic when policies or automation add
servers during traffic peaks and remove them during low traffic. Elasticity helps
control cost because resources do not remain over-provisioned forever.

| Concept | Meaning | Example |
|---|---|---|
| Vertical scaling | Make one resource bigger | Upgrade VM from 4 GB RAM to 16 GB RAM |
| Horizontal scaling | Add more resources | Add five web server instances |
| Diagonal scaling | Combine both approaches | Use medium VMs and add more during demand |
| Elasticity | Automatically match resources to demand | Autoscaling adds instances at peak time |

Capacity planning means estimating how much compute, storage, network and
database capacity a system needs. Traditional capacity planning often required
buying enough hardware for peak demand, which left resources idle most of the
time. Cloud changes this by allowing resources to be added on demand. However,
capacity planning does not disappear. Teams still need to set scaling limits,
choose instance types, design databases and control cost.

A streaming platform is a good example. Suppose a video streaming service has
normal traffic during weekdays but very high traffic during a live sports final.
Vertical scaling alone may not be enough because one server cannot serve all
viewers. Horizontal scaling can add more streaming nodes, caches and application
servers. Elasticity can automatically increase resources before or during the
event and reduce them afterward. A content delivery network can place video
content closer to users, reducing load on the origin servers.

Scalability must be designed at every layer. Web servers can scale horizontally
behind a load balancer. Application services can be split into microservices.
Databases may use read replicas, partitioning or managed scaling. Storage can
use object storage that grows automatically. Caches can reduce repeated database
queries. Messaging queues can absorb sudden bursts of work. If one layer cannot
scale, it becomes the bottleneck.

Students should remember that cloud does not automatically make a bad
application scalable. If an application stores session data only in local memory,
adding more servers may break user sessions. If all requests depend on one
database table without indexing, compute scaling may not solve slow queries.
Cloud provides scalable resources, but application architecture must use them
correctly.

16. SECURITY AND COMPLIANCE IN CLOUD MODELS
================================================================================

Security in cloud computing means protecting cloud systems, applications and
data from unauthorized access, misuse, disruption, leakage and loss. Compliance
means following laws, regulations, standards and policies that apply to data and
systems. Unit 5 usually studies cloud security in greater depth, so Unit 2 should
keep the discussion proportional. The main goal here is to connect security and
compliance with cloud models, especially shared responsibility.

The shared responsibility model changes by service model. In IaaS, the provider
secures the physical data center, hardware, core networking and virtualization
layer. The customer secures the operating system, installed software, firewall
rules, applications, identities and data. In PaaS, the provider also manages the
operating system, runtime and platform, while the customer secures code, data,
configuration and access. In SaaS, the provider manages the full application
stack, while the customer manages users, permissions, data classification and
safe usage.

| Security area | IaaS | PaaS | SaaS |
|---|---|---|---|
| Physical data center | Provider | Provider | Provider |
| Virtualization/infrastructure | Provider | Provider | Provider |
| Operating system | Customer | Provider | Provider |
| Runtime/platform | Customer | Provider | Provider |
| Application code | Customer | Customer | Provider |
| Data and access decisions | Customer | Customer | Shared, with customer configuration |

Identity and Access Management, or IAM, is one of the most important cloud
security controls. IAM defines who can access what. It includes users, groups,
roles, policies, service accounts and multi-factor authentication. The principle
of least privilege says users and services should receive only the permissions
they need. Over-permissioned accounts are dangerous because stolen credentials
can cause large damage.

Encryption protects data by converting it into unreadable form unless the proper
key is available. Data at rest should be encrypted in storage, databases and
backups. Data in transit should be protected using protocols such as HTTPS and
TLS. Key management is also important because encryption is only as strong as
the protection of its keys. Cloud providers offer managed key services, but
customers must configure usage and access correctly.

Network security controls traffic flow. Virtual networks, subnets, security
groups, firewalls, private endpoints, VPNs and web application firewalls help
limit exposure. A common secure pattern is to place public-facing load balancers
in public subnets, application servers in controlled subnets and databases in
private subnets. Network segmentation reduces the impact of a compromise because
attackers cannot freely move everywhere.

Monitoring and logging help detect problems. Cloud environments generate logs
for user activity, API calls, network traffic, application errors and security
events. Monitoring collects metrics such as CPU usage, latency, error rate and
disk usage. Alerts notify teams when abnormal behavior appears. Without logging,
an organization may not know what happened during an incident.

Backup and disaster recovery protect against data loss and service disruption.
Backups should be regular, tested and stored securely. Disaster recovery planning
defines how systems are restored after major failures. Cloud makes backup and
replication easier, but it does not remove the need for planning. A backup that
is never tested may fail when it is most needed.

Common cloud security challenges include misconfigured storage buckets,
excessive permissions, weak passwords, insecure APIs, lack of patching,
unmonitored workloads, data residency issues and misunderstanding shared
responsibility. Many incidents happen because customers assume the provider
handles everything. A strong answer should state clearly that cloud providers
offer tools and secure infrastructure, but customers must configure and use them
properly.

Compliance is important because organizations may handle personal data, payment
data, health records, education records or government information. Regulations
and standards may require encryption, audit logs, access reviews, data location
controls, retention policies and incident reporting. Cloud providers often
publish compliance certifications, but customers must still build compliant
applications and processes on top of the cloud.

Security differs across deployment models. Public cloud requires strong logical
isolation and careful configuration. Private cloud gives more control but also
more responsibility. Hybrid cloud requires consistent security across both
environments. Community cloud requires shared governance among participating
organizations. Therefore security is not a one-size-fits-all topic; it must
match the chosen model.

17. PRICING MODELS AND COST MANAGEMENT
================================================================================

Cloud pricing converts computing from fixed ownership cost into flexible service
cost. Instead of buying all hardware in advance, customers pay according to the
resources and services they consume. This flexibility is one of the main benefits
of cloud computing, but it also creates the risk of unexpected bills if resources
are not monitored.

Pay-as-you-go pricing charges customers based on actual usage. A virtual machine
may be billed per second or per hour, storage per GB per month, data transfer per
GB and serverless functions per request and execution duration. Pay-as-you-go is
excellent for experimentation, variable workloads and temporary projects. Its
limitation is that continuous long-running usage may become expensive if no
discount strategy is used.

Reserved pricing gives discounts when customers commit to using resources for a
longer period, such as one year or three years. Reserved instances, savings
plans and committed use discounts are examples. This model is useful for stable,
predictable workloads such as production databases or always-on application
servers. The risk is that the customer may overcommit and pay for capacity that
is no longer needed.

Spot or preemptible pricing offers unused provider capacity at a large discount.
The provider can interrupt the resource when capacity is needed elsewhere. This
model is useful for fault-tolerant, flexible workloads such as batch processing,
data analysis, rendering and test jobs. It is not suitable for critical systems
that cannot tolerate interruption unless designed carefully.

Subscription pricing is common in SaaS and some platform services. Customers pay
a fixed monthly or annual amount, often per user, per feature tier or per
organization. Subscription pricing is predictable, but unused accounts can waste
money. A company with 500 purchased SaaS licenses and only 300 active users is
paying for unused value.

Cloud cost factors include compute instance size and runtime, storage type and
volume, data transfer, database capacity, backups, snapshots, monitoring logs,
premium support, region choice, load balancers, IP addresses, API calls and
managed service tiers. Students often remember compute cost but forget network
egress and storage growth. In real systems, logs and backups can also become
significant costs if retention is not managed.

FinOps is the discipline of managing cloud cost through collaboration among
engineering, finance and business teams. For students, the practical idea is
simple: cloud cost should be visible, measured and optimized continuously. Good
FinOps habits include tagging resources by project, setting budgets and alerts,
turning off unused resources, selecting right-sized instances, using reserved
pricing for stable workloads, using spot capacity for interruptible jobs and
reviewing bills regularly.

Right-sizing means choosing resource sizes that match real usage. If a virtual
machine uses only 5 percent CPU most of the time, it may be too large. If a
database is constantly overloaded, it may be too small or poorly designed.
Right-sizing should be based on monitoring data rather than guesswork. It is a
simple but powerful cloud cost management practice.

Cost management also includes architecture choices. A serverless function may be
cheaper than an always-running server for occasional tasks. Object storage may
be cheaper than block storage for static files. A content delivery network may
reduce bandwidth and improve performance for global users. PaaS may cost more
per resource but save staff time. Therefore cost should be evaluated as total
cost of ownership, not only the price of one server.

For exam answers, explain pricing models first and then discuss cost management
practices. Use examples such as shutting down unused lab VMs, using budgets,
tagging resources and selecting suitable storage classes. This makes the answer
practical and student-friendly.

18. DECISION GUIDES FOR CHOOSING MODELS
================================================================================

Choosing a cloud model is a decision process, not a guessing game. The correct
choice depends on control requirements, development speed, security needs,
budget, compliance, workload pattern, existing skills and migration complexity.
In exams, decision guide answers show maturity because they connect models to
real situations.

Choose IaaS when you need control over the operating system, network, installed
software or legacy environment. IaaS is also suitable when migrating existing
applications that cannot easily be rewritten. For example, an old inventory
system that runs on a specific OS version may be moved to a cloud VM. The
organization gains flexible infrastructure while avoiding a full application
rewrite.

Choose PaaS when you want to develop and deploy applications quickly without
managing servers. PaaS is suitable for web apps, APIs, student projects,
startups and teams with limited operations staff. The team should be comfortable
with the runtime and platform restrictions. If the application needs unusual OS
configuration, PaaS may not be the best choice.

Choose SaaS when the requirement is a standard business function and a ready
product exists. Email, document collaboration, CRM, video meetings and learning
management are good examples. SaaS is not ideal when the organization needs
deeply unique workflows that cannot be configured inside the product.

Choose public cloud when speed, scalability, global reach and service variety
matter more than physical ownership. Choose private cloud when control,
compliance, data sensitivity or dedicated infrastructure dominates. Choose hybrid
cloud when some workloads must remain private but others benefit from public
cloud. Choose community cloud when several organizations share common regulatory
or mission requirements.

Choose containers when the application should be portable, consistently packaged
and deployed across environments. Containers are strong for microservices and
DevOps workflows. Choose serverless when the workload is event-driven,
irregular, short-running and benefits from automatic scaling. Choose virtual
machines when full OS control, legacy compatibility or strong isolation is
needed.

Decision guides should also consider team skills. A small team may benefit from
SaaS or PaaS because it cannot manage complex infrastructure. A mature DevOps
team may choose Kubernetes or IaaS for flexibility. A regulated enterprise may
combine models carefully. The best cloud model is not always the most advanced
one; it is the one that fits the problem and constraints.

19. FUTURE SCOPE AND CAREER RELEVANCE
================================================================================

Cloud computing models are not only theoretical categories. They are directly
connected to modern IT careers. Cloud architects, DevOps engineers, site
reliability engineers, platform engineers, cloud security analysts, FinOps
analysts, data engineers and AI engineers all use these models when designing
and operating systems. Understanding Unit 2 helps students speak the language of
real cloud projects.

The future of cloud includes hybrid cloud, multi-cloud, edge computing,
serverless platforms, container orchestration, AI cloud services, industry
clouds and stronger security automation. Organizations rarely use one model
only. A real company may run Kubernetes for microservices, serverless functions
for event processing, SaaS for HR, DBaaS for databases and public-private hybrid
cloud for compliance. The ability to combine models intelligently is becoming a
valuable skill.

Edge cloud will grow because many applications need low latency and local data
processing. Smart factories, autonomous vehicles, healthcare devices, augmented
reality and real-time video analytics cannot always send every event to a
distant data center. Edge computing brings cloud-style management closer to
where data is created.

Serverless and managed services will continue to reduce operational burden. Many
developers will build applications by composing managed databases, queues,
identity services, APIs and functions. This increases speed but also requires
careful design to avoid lock-in, cost surprises and security mistakes.

Cloud security and compliance careers will grow because organizations need
people who understand shared responsibility, identity, encryption, network
controls and audit requirements. FinOps careers will also grow because cloud
cost has become a major business concern. Technical knowledge combined with cost
awareness is highly valued.

For students, Unit 2 is a gateway to practical learning. If you understand IaaS,
you can create and secure a virtual machine. If you understand PaaS, you can
deploy a web application quickly. If you understand SaaS, you can evaluate
business tools. If you understand containers and serverless, you can start
learning modern cloud-native development.

20. MEMORY TRICKS AND MNEMONICS
================================================================================

The SPI stack can be remembered as "Software sits on Platform, Platform sits on
Infrastructure." This sentence helps because it shows the order from top to
bottom. SaaS is closest to the user, PaaS is closest to the developer, and IaaS
is closest to the administrator.

The control-convenience ladder can be remembered as "I control, P deploys, S
uses." In IaaS, the customer controls infrastructure details. In PaaS, the
developer deploys code to a managed platform. In SaaS, the user simply uses the
application. This memory trick helps identify service models in examples.

Deployment models can be remembered as "Public is provider-shared, Private is
organization-dedicated, Hybrid is mixed, Community is common-purpose." This is
longer than a single acronym, but it prevents confusion. The key words are
shared, dedicated, mixed and common-purpose.

The NIST actors can be remembered using "Consumer Picks, Provider Runs, Auditor
Checks, Broker Helps, Carrier Connects." Consumer uses or selects the service.
Provider operates it. Auditor verifies it. Broker assists with selection or
integration. Carrier provides network connectivity. This sentence gives each
actor an action.

Load balancing algorithms can be remembered as "Round, Weight, Few, Fast, Hash."
Round means Round Robin. Weight means Weighted Round Robin. Few means Least
Connections. Fast means Least Response Time. Hash means hash-based routing. The
short phrase helps during revision, but the exam answer should still explain
each algorithm in full sentences.

Scaling can be remembered as "Up, Out, Both, Auto." Up means vertical scaling,
out means horizontal scaling, both means diagonal scaling and auto means
elasticity. This memory trick is simple but powerful because students often mix
vertical scaling and horizontal scaling.

Shared responsibility can be remembered as "Provider protects the cloud;
customer protects what they put in the cloud." This popular phrase is not a
complete legal rule, but it captures the basic idea. In IaaS, the customer puts
more inside the cloud and therefore protects more. In SaaS, the customer mainly
protects accounts, data choices and configuration.

For pricing, remember "Use, Commit, Interrupt, Subscribe." Use means pay-as-you-
go. Commit means reserved or savings pricing. Interrupt means spot or
preemptible capacity. Subscribe means SaaS-style subscription. This helps
students write pricing model answers with examples.

21. CONFUSING PAIRS EXPLAINED IN PARAGRAPH FORM
================================================================================

IaaS and PaaS are often confused because both can be used by developers. The
difference is the level of management. In IaaS, the customer receives virtual
machines and must manage operating systems and runtime installation. In PaaS,
the customer receives a ready application platform and focuses on code. If the
question mentions selecting VM size and installing software, it is likely IaaS.
If it mentions pushing code to a managed runtime, it is likely PaaS.

PaaS and SaaS are often confused because both hide infrastructure from users.
The difference is whether the customer builds an application or uses a completed
application. In PaaS, the customer is usually a developer deploying code. In
SaaS, the customer is usually an end user using finished software. Heroku is
PaaS because developers deploy applications to it. Gmail is SaaS because users
use email without building the email application.

Public cloud and private cloud are confused when students focus only on internet
access. A private cloud may still be accessible over a network, and a public
cloud may include private networking features. The true distinction is ownership
and tenancy. Public cloud is provider-owned and shared among many customers.
Private cloud is dedicated to one organization.

Hybrid cloud and multi-cloud are also confused. Hybrid cloud combines private
and public environments into a coordinated architecture. Multi-cloud uses more
than one cloud provider. A company using AWS and Azure is multi-cloud. A company
using its own private cloud plus AWS is hybrid cloud. A company can be both
hybrid and multi-cloud if it uses private cloud plus several public providers.

Scalability and elasticity are related but not identical. Scalability means the
system can handle growth. Elasticity means the system automatically adjusts
resources according to demand. A manually expanded database server is scalable
but not necessarily elastic. An autoscaling web tier that adds and removes
instances based on traffic is elastic.

Containers and virtual machines are confused because both isolate workloads.
Virtual machines include separate guest operating systems and virtualize
hardware. Containers share the host kernel and package applications with their
dependencies. VMs are heavier but provide full OS-level separation. Containers
are lighter and more portable for application deployment.

Serverless and SaaS are confused because both hide servers. In SaaS, the user
uses a complete application. In serverless, the developer writes functions or
uses event-driven managed components. Serverless is a development and execution
model, while SaaS is an application delivery model.

Cloud broker and cloud carrier are confused in the NIST reference model. A
broker helps select, manage, integrate or add value to cloud services. A carrier
provides network connectivity between consumers and providers. In simple words,
the broker helps with cloud service usage, while the carrier carries the network
traffic.

22. MODEL EXAM ANSWER STRUCTURES FOR 5 TO 10 MARK QUESTIONS
================================================================================

For a 5-mark answer on IaaS, begin with a clear definition. Then explain that
the provider offers virtualized compute, storage and networking while the
customer manages operating systems, applications and data. Add two benefits such
as scalability and reduced upfront cost. Add two limitations such as management
overhead and security responsibility. End with examples such as AWS EC2, Azure
VMs or Google Compute Engine. A small diagram of user, internet and virtual
resources can improve the answer if time permits.

For a 5-mark answer on PaaS, define it as a managed platform for developing and
deploying applications. Explain that developers bring code while the provider
manages servers, operating systems, runtime and platform services. Mention
benefits such as faster development and simplified deployment. Mention
limitations such as reduced control and possible lock-in. Give examples such as
Heroku, Google App Engine and Azure App Service.

For a 5-mark answer on SaaS, define it as complete software delivered over the
internet. Explain that users access it through browsers or apps while the
provider manages the full application stack. Mention benefits such as easy
access, automatic updates and subscription pricing. Mention limitations such as
limited customization and dependency on provider availability. Give examples
such as Gmail, Microsoft 365 and Salesforce.

For a 10-mark comparison of IaaS, PaaS and SaaS, begin with a short introduction
to the SPI stack. Then create a comparison table with columns for model, what is
provided, user responsibility, provider responsibility, advantages, limitations
and examples. After the table, write explanatory paragraphs about the
control-versus-convenience trade-off. End with a practical example showing which
model fits which situation.

For a 10-mark answer on deployment models, define deployment model first. Then
explain public, private, hybrid and community cloud in separate paragraphs. For
each, include ownership, access, advantages, limitations and examples. Add a
comparison table if time allows. End by saying that deployment choice depends on
security, cost, scalability, compliance and control requirements.

For a 10-mark answer on cloud architecture, begin with a definition and then
describe front end, network and back end. Explain compute, storage,
virtualization, management, security, monitoring and load balancing. Draw a
simple architecture diagram with users, internet, load balancer, application
servers, database, storage and management services. End by explaining that good
architecture supports scalability, availability and security.

For a 10-mark answer on the NIST reference model, define the reference model as
a framework describing cloud actors and relationships. Explain Cloud Consumer,
Cloud Provider, Cloud Auditor, Cloud Broker and Cloud Carrier in full
paragraphs. Give a real example, such as a university consuming SaaS from a
provider through an internet carrier, with an auditor checking compliance and a
broker helping manage services. A diagram with five actors can make the answer
clear.

For a 10-mark answer on containers, Docker and serverless, start with containers
and explain why they solve environment consistency. Compare containers and
virtual machines. Then explain Docker workflow: Dockerfile, image, registry and
container. Finally explain serverless as event-driven execution without direct
server management, compare it with PaaS and give examples. This structure covers
both depth and comparison.

For a 10-mark answer on load balancing, define load balancing and state why it is
needed. Explain the five-step working from user request to backend routing.
Describe algorithms such as Round Robin, Weighted Round Robin, Least
Connections, Least Response Time and Hash. Compare software and hardware load
balancers and mention cloud examples. Draw a diagram with one load balancer and
multiple application servers.

For a 10-mark answer on security and compliance, keep the answer proportional to
Unit 2. Start with shared responsibility. Compare IaaS, PaaS and SaaS security
responsibilities. Explain IAM, encryption, network controls, monitoring, backup
and compliance. End with common challenges such as misconfiguration and excessive
permissions. Do not turn the whole answer into deep cryptography, because that
belongs more to a security-focused unit.

23. COMMON MISTAKES STUDENTS MAKE
================================================================================

One common mistake is mixing service models and deployment models. Students may
write that public cloud, private cloud and hybrid cloud are service models, or
that IaaS and SaaS are deployment models. The correction is simple: service
models describe what is delivered, while deployment models describe where it
runs and who uses it.

Another common mistake is saying that cloud always reduces cost. Cloud can
reduce cost when resources are used efficiently, but it can increase cost when
resources are oversized, idle or poorly monitored. A better statement is that
cloud changes cost from upfront capital expense to usage-based operational
expense and gives opportunities for optimization.

Students often write that SaaS means "software installed from the internet."
This is incomplete. SaaS means the software is hosted and managed by the
provider and accessed over a network. Downloading an installer from a website is
not automatically SaaS. The management and delivery model matter.

Another mistake is assuming serverless means no servers exist. Servers still
exist, but the customer does not manage them directly. The provider provisions,
scales and maintains the infrastructure. The term "serverless" refers to the
customer experience and operating model, not the absence of physical machines.

Students may write that containers are the same as virtual machines. Containers
are lighter because they share the host operating system kernel, while virtual
machines include full guest operating systems. Both isolate workloads, but their
abstraction levels and resource usage differ.

Some answers list cloud examples without explaining the model. For example,
writing only "AWS, Azure, Google" does not answer a question on IaaS. A better
answer says that AWS EC2 is IaaS because it provides virtual machines, while
Google App Engine is PaaS because it provides a managed application platform,
and Gmail is SaaS because it provides a complete email application.

Students often ignore shared responsibility in security answers. They may write
that the provider handles all security. This is dangerous and incorrect. Even in
SaaS, customers must manage user access, permissions and data sharing. In IaaS,
customers have much more responsibility.

Another mistake is describing hybrid cloud as simply using public cloud and
private cloud separately. True hybrid cloud requires some level of integration,
such as shared identity, network connectivity, data movement or coordinated
management. Without integration, it may only be two separate environments.

Students sometimes memorize load balancing algorithms but fail to explain why
load balancing is needed. Always begin with the purpose: distributing traffic,
improving performance, improving availability and supporting scaling. Then
explain algorithms.

A final mistake is drawing diagrams without explanation. Diagrams are useful,
but examiners need written meaning. Label the diagram clearly and explain the
flow in words. A simple diagram plus a clear paragraph is better than a complex
unexplained drawing.

24. VIVA AND ORAL QUESTION BANK WITH FULL-SENTENCE ANSWERS
================================================================================

Q1. What is a cloud service model?
Answer: A cloud service model is a way of classifying cloud services according
to what capability is delivered to the customer and how responsibility is shared
between the provider and the customer. The main service models are IaaS, PaaS
and SaaS.

Q2. What is the main difference between IaaS and PaaS?
Answer: In IaaS, the customer receives infrastructure such as virtual machines,
storage and networks and manages the operating system and applications. In PaaS,
the customer receives a ready platform for deploying code, while the provider
manages the servers, operating system and runtime.

Q3. Give one example of SaaS and explain why it is SaaS.
Answer: Gmail is an example of SaaS because users access a complete email
application over the internet, and Google manages the servers, software updates,
storage and most backend operations.

Q4. What is a deployment model?
Answer: A deployment model describes how a cloud environment is owned, accessed
and shared. Public, private, hybrid and community cloud are the main deployment
models.

Q5. Why is public cloud popular?
Answer: Public cloud is popular because it provides fast provisioning, global
availability, scalability, many managed services and pay-as-you-go pricing
without requiring customers to buy and maintain physical infrastructure.

Q6. Why might an organization choose private cloud?
Answer: An organization may choose private cloud when it needs dedicated
infrastructure, stronger control, custom security policies or compliance with
strict regulations that are difficult to satisfy in a general shared public
cloud environment.

Q7. What is hybrid cloud?
Answer: Hybrid cloud is a deployment model that integrates private cloud and
public cloud environments so that workloads, data or management can coordinate
across them. It is useful when some systems need control and others need public
cloud scalability.

Q8. What are the five NIST cloud actors?
Answer: The five NIST cloud actors are Cloud Consumer, Cloud Provider, Cloud
Auditor, Cloud Broker and Cloud Carrier. They represent the user, service
operator, independent assessor, intermediary and network connectivity provider.

Q9. What is multi-tenancy?
Answer: Multi-tenancy is a cloud design in which multiple customers share the
same underlying infrastructure or application while their data and configuration
remain logically separated.

Q10. Why is load balancing important in cloud?
Answer: Load balancing is important because it distributes requests across
multiple resources, improves performance, avoids overload, supports scaling and
helps maintain availability when some servers fail.

Q11. What is the difference between vertical and horizontal scaling?
Answer: Vertical scaling increases the capacity of one machine, such as adding
more CPU or memory. Horizontal scaling adds more machines or instances and
distributes work across them.

Q12. What is elasticity?
Answer: Elasticity is the ability of a cloud system to automatically add or
remove resources based on current demand, so the system can handle peaks without
paying continuously for unused capacity.

Q13. What is Docker?
Answer: Docker is a platform used to build, package, distribute and run
containers. It uses Dockerfiles to create images, registries to store images and
containers to run applications from those images.

Q14. Is serverless computing actually server-free?
Answer: No. Serverless computing still uses servers, but the cloud provider
manages them. The customer writes code or configures services without directly
provisioning or maintaining servers.

Q15. What is shared responsibility?
Answer: Shared responsibility means the cloud provider and the customer divide
security and management duties. The provider protects the cloud infrastructure,
while the customer protects data, access and configuration according to the
service model.

Q16. Why is IAM important in cloud?
Answer: IAM is important because it controls who can access cloud resources and
what actions they can perform. Correct IAM reduces the risk of unauthorized
access and limits damage if credentials are compromised.

Q17. What is pay-as-you-go pricing?
Answer: Pay-as-you-go pricing means customers are charged based on actual
resource usage, such as compute time, storage volume, data transfer or number of
requests.

Q18. What is a reserved instance or committed use discount?
Answer: It is a pricing model where customers receive a discount by committing
to use resources for a longer period. It is suitable for predictable workloads.

Q19. What is the difference between a cloud broker and cloud carrier?
Answer: A cloud broker helps consumers select, integrate or manage cloud
services, while a cloud carrier provides the network connectivity that transports
cloud services between provider and consumer.

Q20. Why are containers useful in cloud computing?
Answer: Containers are useful because they package applications with
dependencies, start quickly, use resources efficiently and make deployment more
consistent across development, testing and production environments.

Q21. What is DBaaS?
Answer: DBaaS is Database as a Service, where a cloud provider offers managed
database services and handles tasks such as provisioning, patching, backups and
monitoring while the customer manages data design and access.

Q22. What is the main risk of multi-tenancy?
Answer: The main risk of multi-tenancy is that weak isolation or incorrect
configuration could allow data leakage, performance interference or unauthorized
access between tenants.

Q23. How does a load balancer know a server has failed?
Answer: A load balancer uses health checks to test backend servers. If a server
fails repeated health checks, the load balancer stops sending traffic to it
until it becomes healthy again.

Q24. Why is compliance important in cloud?
Answer: Compliance is important because organizations may handle sensitive data
that must follow legal, regulatory or industry requirements. Cloud customers
must ensure their architecture, controls and provider choices meet those
requirements.

Q25. What is vendor lock-in?
Answer: Vendor lock-in occurs when an application or business process becomes
strongly dependent on one provider's services, APIs or data formats, making
migration to another provider difficult or costly.

25. PRACTICAL LAB CONNECTIONS
================================================================================

Unit 2 connects directly to cloud laboratory work because every practical task
usually demonstrates one or more cloud models. When students create a virtual
machine, they are practicing IaaS. They choose compute size, operating system,
network settings and storage. This practical experience makes the IaaS
responsibility model clear because students must log in, install software,
configure security and stop the machine when finished.

When students deploy a small web application to a managed platform, they are
practicing PaaS. The platform may ask for code, runtime version, environment
variables and deployment commands, but it hides server provisioning. This
practical shows why PaaS is useful for developers. The student experiences the
difference between managing a full virtual machine and simply deploying code.

When students use online office tools, cloud email, learning management systems
or collaboration platforms, they are using SaaS. A practical can ask students to
identify what the provider manages and what the user manages. For example, in a
learning management SaaS, the provider manages the software platform, but the
teacher manages course content, student access and settings.

Creating storage buckets or uploading files to cloud object storage demonstrates
Storage as a Service. Students should observe permissions, public access
settings, versioning and lifecycle rules. This connects to security because a
misconfigured storage bucket can expose data publicly. It also connects to cost
because storage classes and retention policies affect billing.

Running a container locally or in a cloud container service demonstrates
containerization and CaaS. A practical may include writing a Dockerfile, building
an image, running a container and mapping ports. This connects to deployment
models because the same image can run on a laptop, private cloud or public cloud
service.

Creating a simple serverless function demonstrates FaaS. A practical may trigger
a function through an HTTP request or file upload. Students should notice that
they do not create a virtual machine. They write function code, configure a
trigger and view logs. This shows the difference between serverless and IaaS.

Configuring a load balancer in a lab demonstrates availability and scaling. A
student can run two simple web servers and place a load balancer in front of
them. By stopping one server, the student can observe whether traffic still
reaches the healthy server. This practical makes the idea of health checks and
traffic distribution concrete.

Autoscaling labs connect to scalability and elasticity. Students can configure a
scaling policy based on CPU usage or request count. When load increases, new
instances are created. When load decreases, extra instances are removed. This is
one of the clearest practical demonstrations of elasticity.

Identity and access management labs connect to shared responsibility. A student
can create users, roles and permissions, then test what actions are allowed or
denied. This shows that even when the provider offers IAM tools, the customer is
responsible for correct configuration.

Cost monitoring labs are also valuable. Students can create a budget alert,
tag resources by project and stop unused resources. This practical teaches that
cloud resources are easy to create but must be managed carefully to avoid
unnecessary cost.

26. REAL-WORLD MINI CASE STUDIES
================================================================================

Case study 1: A college wants to host an online admission portal for two months.
The traffic will be very high near the application deadline and low afterward.
Buying physical servers would be wasteful because the demand is temporary. A
public cloud architecture using IaaS or PaaS is suitable. If the college has a
small development team, PaaS may be better because it reduces server management.
The application can use managed database services, object storage for documents,
load balancing and autoscaling. This case shows how cloud supports temporary and
variable workloads.

Case study 2: A hospital stores patient records and must follow strict privacy
rules. It may choose a private cloud or a carefully governed hybrid cloud.
Sensitive records can remain in a private environment, while public cloud can be
used for appointment reminders, educational content or non-sensitive analytics.
The design must include IAM, encryption, audit logs, backup and compliance
checks. This case shows that cloud choice depends not only on technology but
also on legal and trust requirements.

Case study 3: A startup builds a food delivery application. At first, the team
has few engineers and wants to release quickly. PaaS, managed databases and
serverless functions are suitable because they reduce operations work. As the
startup grows, it may move some services into containers on Kubernetes for
greater control. This case shows how cloud model choices can evolve with scale
and team maturity.

Case study 4: A media company streams a live concert. The workload is extremely
high during the event and drops afterward. The company can use public cloud,
content delivery networks, horizontal scaling, load balancing and autoscaling.
Object storage can store video files, and global load balancing can route users
to nearby regions. This case shows scalability, elasticity and load balancing
working together.

Case study 5: A software company offers accounting software to thousands of
small businesses. SaaS is the natural model because customers want a finished
application, not servers. The provider may use multi-tenant architecture to
serve many customers efficiently. Data isolation, tenant-specific configuration,
backup and audit logs are important. This case shows how SaaS, multi-tenancy and
shared responsibility combine.

Case study 6: A research lab needs thousands of compute cores for a short
simulation. Public cloud IaaS with spot or preemptible instances may be suitable
because the workload is temporary and fault-tolerant. The lab can checkpoint
progress and restart interrupted jobs. This case shows how pricing models affect
technical architecture.

Case study 7: A bank uses SaaS for email, private cloud for core banking and
public cloud analytics for anonymized data. This is a hybrid and multi-service
environment. The bank must manage identity, encryption, monitoring and
compliance across all systems. This case shows that real organizations rarely
use only one cloud model.

Case study 8: An online exam platform must handle many students logging in at
the same time. It needs load balancing, autoscaling, database scaling, monitoring
and backup. Security controls must prevent unauthorized access and protect exam
data. The platform may use containers for application services and managed
databases for reliability. This case connects directly to education-sector cloud
usage.

27. ARCHITECTURE DRAW-IN-EXAM CHEAT SHEET
================================================================================

When asked to draw cloud architecture in an exam, do not try to draw every real
cloud service. Draw a clear logical view. The diagram should show users, network
access, load balancing, application or service layer, data layer, storage,
management and security. A simple labeled diagram is better than a crowded
diagram with many unclear icons.

In prose, explain that users access the application through a browser or mobile
app. The network carrier and DNS bring traffic to the cloud. The load balancer
receives requests and distributes them to healthy application servers. The
application servers may run as virtual machines, containers or platform-managed
services. The database stores structured data, while object storage stores files
and backups. Management services monitor performance, enforce access control,
manage encryption and record billing.

For an IaaS answer, label the application servers as virtual machines and say
the customer manages operating systems and applications. For a PaaS answer,
label them as managed application instances and say the provider manages the
runtime. For a container answer, label them as containers or pods. For a
serverless answer, replace app servers with functions and event triggers. This
adaptation skill helps you reuse one diagram intelligently in many exam
questions.

For the NIST reference model, draw the Cloud Consumer on the left and Cloud
Provider on the right. Place Cloud Carrier between them as the network. Place
Cloud Broker above or between consumer and provider as an optional intermediary.
Place Cloud Auditor near the provider with an arrow showing assessment. Then
explain each actor in words.

For load balancing, draw many users pointing to one load balancer, and the load
balancer pointing to multiple servers. Add health checks from the load balancer
to servers. If one server is crossed out, show traffic going only to healthy
servers. This makes the availability concept clear.

For hybrid cloud, draw a private cloud box and public cloud box connected by a
VPN or dedicated link. Put sensitive database or internal systems in private
cloud and scalable web or analytics services in public cloud. Explain that
hybrid cloud requires integration, not just separate usage.

28. CROSS-CONNECTIONS TO OTHER UNITS
================================================================================

Unit 2 connects strongly to Unit 1 because cloud models are built on the
characteristics introduced earlier, such as on-demand self-service, broad network
access, resource pooling, rapid elasticity and measured service. IaaS, PaaS and
SaaS are practical forms of these characteristics. For example, measured service
appears in pay-as-you-go pricing, and resource pooling appears in multi-tenancy.

Unit 2 connects to virtualization because IaaS depends heavily on virtual
machines, hypervisors and resource abstraction. When you study virtualization,
remember that it is one of the main enabling technologies behind cloud
infrastructure. Containers add another abstraction that is lighter than virtual
machines and important for cloud-native architecture.

Unit 2 connects to storage units because cloud service models use different
types of storage. IaaS may use block storage for VM disks. PaaS may attach
managed databases. SaaS hides most storage details from users. Object storage,
backup, replication and lifecycle policies are practical storage topics that
support cloud applications.

Unit 2 connects to networking because cloud deployment models require virtual
networks, subnets, routing, DNS, VPNs, load balancers and content delivery
networks. Hybrid cloud especially depends on secure networking between private
and public environments. Load balancing and global traffic management are also
network topics.

Unit 2 connects to security units through shared responsibility, IAM,
encryption, monitoring and compliance. Later security chapters may go deeper
into attacks, cryptography and governance, but Unit 2 provides the model-based
foundation. Security responsibilities differ depending on IaaS, PaaS, SaaS and
deployment type.

Unit 2 connects to cloud platforms because real providers offer concrete
services that map to these models. AWS EC2 maps to IaaS, Elastic Beanstalk and
App Runner map to PaaS-like services, Lambda maps to serverless, S3 maps to
storage service and Salesforce maps to SaaS. Similar mappings exist in Azure and
Google Cloud.

Unit 2 connects to practical exams because every lab has a model behind it. A VM
lab is IaaS. A cloud app deployment lab is PaaS. A function lab is serverless.
A Docker lab is containerization. An IAM lab demonstrates shared responsibility.
Recognizing the model behind the practical helps answer viva questions.

29. FIVE-MINUTE RAPID REVISION, SELF-TEST AND FINAL CHECKLIST
================================================================================

Five-minute rapid revision begins with the SPI stack. IaaS provides virtualized
infrastructure and gives the most control. PaaS provides a managed application
platform and helps developers deploy quickly. SaaS provides complete
applications and gives users the most convenience. Moving from IaaS to SaaS,
provider management increases and customer technical control decreases.

Next revise deployment models. Public cloud is provider-owned and shared among
many customers. Private cloud is dedicated to one organization. Hybrid cloud
integrates private and public environments. Community cloud is shared by
organizations with common requirements. Remember that deployment model is about
ownership, access and sharing, while service model is about what capability is
delivered.

Then revise architecture. Cloud architecture includes front end, network, back
end, virtualization, storage, management, monitoring, security and billing. Load
balancers distribute traffic to multiple servers. Autoscaling adds or removes
resources. IAM controls access. Encryption protects data. Monitoring and logging
show system health and support security investigation.

Then revise the NIST actors. Cloud Consumer uses services. Cloud Provider offers
and operates services. Cloud Auditor checks security, performance and
compliance. Cloud Broker helps select, integrate or manage services. Cloud
Carrier provides connectivity. The mnemonic is: Consumer Picks, Provider Runs,
Auditor Checks, Broker Helps, Carrier Connects.

Then revise containers and serverless. Containers package applications with
dependencies and share the host kernel. Docker builds images from Dockerfiles,
stores them in registries and runs them as containers. Serverless runs code or
managed services without direct server management, usually in response to
events. Containers are strong for portability; serverless is strong for
event-driven automatic scaling.

Self-test question 1: A company wants complete control over OS configuration and
network settings. Which service model fits best? The answer is IaaS because it
provides virtual machines and infrastructure-level control.

Self-test question 2: A developer wants to deploy code without managing servers.
Which service model fits best? The answer is PaaS because the provider manages
the runtime and platform while the developer manages code.

Self-test question 3: A business wants ready email and document collaboration.
Which service model fits best? The answer is SaaS because users need a complete
application rather than infrastructure or a development platform.

Self-test question 4: A hospital keeps patient records on a dedicated cloud but
uses public cloud for appointment reminders. Which deployment model is this?
The answer is hybrid cloud because private and public environments are combined
for different workloads.

Self-test question 5: What algorithm sends traffic to the server with the fewest
active sessions? The answer is Least Connections.

Self-test question 6: What is the main difference between scalability and
elasticity? Scalability is the ability to handle growth, while elasticity is the
automatic adjustment of resources according to demand.

Self-test question 7: Why does multi-tenancy reduce cost? It reduces cost
because multiple tenants share the same infrastructure or application, allowing
the provider to use resources more efficiently.

Self-test question 8: What is the main security lesson of shared
responsibility? The provider secures the cloud infrastructure, but the customer
must secure data, access, configuration and the parts of the stack controlled by
the customer.

Self-test question 9: When is spot or preemptible pricing suitable? It is
suitable for interruptible workloads such as batch jobs, simulations, rendering
or test tasks that can restart if the provider takes capacity back.

Self-test question 10: Why is a broker different from a carrier? A broker helps
with cloud service selection, integration or management, while a carrier
provides the network connection that transports the service.

Final checklist for Unit 2: You should be able to define IaaS, PaaS and SaaS in
full sentences. You should be able to compare them by control, responsibility,
advantages, limitations and examples. You should be able to explain public,
private, hybrid and community cloud without confusing them with service models.
You should be able to draw a basic cloud architecture diagram and explain each
component. You should be able to name and explain the five NIST actors.

You should also be able to explain containers, Docker workflow and serverless
computing. You should be able to compare containers with virtual machines and
PaaS with serverless. You should be able to explain multi-tenancy, including
three architecture styles and their pros and cons. You should be able to explain
load balancing, its five-step working and common algorithms. You should be able
to explain vertical, horizontal and diagonal scaling, and the difference between
scalability and elasticity.

Before the exam, practice writing at least three model answers: one comparison
of IaaS, PaaS and SaaS, one answer on deployment models, and one answer on cloud
architecture with a diagram. Practice one answer on NIST actors and one answer
on load balancing or scalability. These questions cover the heart of Unit 2 and
also connect to practical cloud work.

The final mental summary is this: cloud models explain what is delivered, where
it runs, who manages it, how it scales, how it is secured and how it is paid for.
If you can connect every model to control, convenience, responsibility, cost,
security and examples, you can write strong answers for almost any Unit 2
question.
